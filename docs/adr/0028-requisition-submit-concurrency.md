# 0028. ส่งใบเบิกพร้อมกันหลายหน่วยงาน — บันทึกเป็นธุรกรรมเดียว + ตรวจยอดจองซ้ำหลังบันทึก

- **Status:** Proposed (11/10/2569 — ยังไม่ลงมือ · ต้องทำก่อนเปิด pilot เบิกยาออนไลน์)
- **Date:** 2026-10-11
- **เกี่ยวข้อง:** [ADR-0004](0004-requisition-at-drug-level-base-unit.md) (เบิกระดับยา หน่วยย่อยสุด) · [ADR-0005](0005-lot-allocation-preview-and-pick-record.md) (FEFO) · [ADR-0016](0016-anon-key-full-db-access.md) (anon key เต็มสิทธิ์) · ที่มา: [docs/reference-mobile-app-videos.md](../reference-mobile-app-videos.md) §3.2 (คลิป "ล็อกที่นั่ง" ที่ไม่ได้ล็อกจริง)

## Context

`submit` ใน [RequisitionApp.jsx](../../src/RequisitionApp.jsx) (บรรทัด ~1185–1262) ทำ 3 ขั้นจาก**เบราว์เซอร์**:

1. อ่าน `fetchInvBaseByCode` (คงเหลือ × packsize จาก `parseUnit`) + `fetchReservedBase` (ยอดจอง 6 สถานะ — pending/approved ตามที่ขอ/อนุมัติ · picking→received ตาม `picked_allocation` จนกว่า import inventory รอบใหม่) แล้วเทียบ `requestedQty ≤ คงเหลือ − จอง`
2. `insert requisitions` (สุ่มเลขใบ retry ถ้าชน unique)
3. `insert requisition_items`

ช่องโหว่ (ไล่โค้ดแล้ว 11/10/2569 — ยังไม่เคยทดสอบด้วยผู้ใช้ 2 คนจริง):

- **จองเกินของ (race):** หน่วยงาน A และ B กดส่งยาตัวเดียวกันพร้อมกัน → ทั้งคู่อ่านขั้น 1 ก่อนอีกฝั่ง insert → เห็น "ว่าง" เท่ากัน → ผ่านทั้งคู่ ยอดจองรวมเกินคงเหลือ. เกิดได้จริงใกล้เส้นตายรอบเบิก (ข้อตกลงแผน Dashboard ข้อ 22: ทุกหน่วยงานส่งวันเดียวกัน)
- **หัวใบเบิกเปล่า:** ขั้น 2 สำเร็จแต่ขั้น 3 ล้ม (เน็ตหลุดบนมือถือ) → ใบ `pending` ไม่มีรายการค้างในคิว staff — ไม่ใช่ธุรกรรมเดียว
- **ใบแก้ไข (requester แก้ใบ pending เดิม)** ใช้ re-validate แบบเดียวกัน (`excludeReqId`) — ช่องเดียวกัน

ความรุนแรง: ปานกลาง — staff ยังจับได้ตอนจัดยา (FEFO คำนวณจากของจริง ADR-0005 ข้อ 2) แต่ผู้เบิกได้ "ส่งสำเร็จ" ทั้งที่ของไม่พอ และต้องตามแก้ทีหลัง

ข้อจำกัดที่บังคับรูปแบบทางแก้:
- **สูตร "พร้อมเบิก" อยู่ใน JS ล้วน** — `parseUnit` (เลขนำของ unit เช่น `1000เม็ด` = packsize, ดู memory unit display กำกวม) + กฎยอดจอง 6 สถานะ + `picked_allocation` jsonb + เวลานำเข้าล่าสุด. เขียนซ้ำใน SQL = ตรรกะ 2 ชุดที่ดริฟต์ (บทเรียนเดียวกับกฎ "แก้ V2 ต้อง sync 4 ที่" ของนโยบายคืนยา)
- PostgREST แต่ละ request = ธุรกรรมแยก → advisory lock ข้าม request ไม่ได้
- repo ยังไม่เคยใช้ `supabase.rpc()` · ไม่มี DB ทดสอบแยก (เขียนลงระบบจริงเท่านั้น)

## Decision (เสนอ)

1. **RPC `submit_requisition(p_header jsonb, p_items jsonb)`** (plpgsql, `security invoker`) — insert หัวใบ (สุ่มเลข + retry เมื่อ `unique_violation` ฝั่ง DB) + รายการ **ในธุรกรรมเดียว** แล้วคืนแถวหัวใบ. ไม่มีตรรกะธุรกิจในฟังก์ชัน (แค่ insert) → แก้หัวใบเปล่า โดยไม่สร้างสูตรชุดที่ 2. เรียกผ่านฟังก์ชันใหม่ใน `db.js` (ย้าย query ของ submit ออกจาก component ไปด้วย — Do Not "component ห้ามเรียก supabase ตรง")
2. **ตรวจซ้ำหลังบันทึก (insert-then-verify):** หลัง RPC สำเร็จ เรียก `fetchInvBaseByCode` + `fetchReservedBase` ตัวเดิม (**รวมใบตัวเองแล้ว**) สำหรับรหัสในใบ → ถ้ารหัสใด `จองรวม > คงเหลือ` = ชนกัน → **ถอนใบตัวเอง** (RPC `withdraw_requisition(id)` ลบหัว+รายการในธุรกรรมเดียว) + audit `requisition_conflict_withdrawn` + บอกผู้ใช้ "มีหน่วยงานอื่นเบิกยานี้พร้อมกัน — ตรวจยอดแล้วส่งใหม่" พร้อมยอดที่เหลือจริง
   - **ทำไมถูกต้อง:** สมมติ A กับ B ผ่านทั้งคู่ทั้งที่ของไม่พอ — การตรวจของแต่ละใบเกิดหลังใบตัวเอง insert แล้ว · การตรวจที่เกิด "ทีหลัง" ของสองใบ เกิดหลังทั้งสองใบ commit และก่อนมีใครถอน (เพราะผ่านทั้งคู่ ไม่มีใครถอน) → ต้องเห็นยอดรวมทั้งสองใบ → ต้องตก · ขัดกัน ∴ **จองเกินพร้อมกันเป็นไปไม่ได้**
   - **ราคาที่จ่าย:** ชนกันจริงอาจถอน**ทั้งสองใบ** (ทั้งคู่ตรวจหลังทั้งคู่ insert) → ผู้ใช้กดส่งใหม่ได้ (ปลอดภัยแต่ไม่เสมอภาค — ยอมรับ เพราะเกิดน้อยและแก้ด้วยกดซ้ำ)
   - ขั้นตรวจเดิมก่อนบันทึกคงไว้ (บอกผู้ใช้เร็วในเคสปกติ ไม่ต้อง insert แล้วถอน)
3. **ใบแก้ไข** ใช้ทางเดียวกัน (RPC แทนรายการ + ตรวจซ้ำ) — ถ้าชน คืนรายการเดิม (ไม่ลบทั้งใบ)
4. **audit/การแจ้งเตือน:** action ใหม่ต้อง sync 4 ที่ (Critical Rule #12: `NOTIF_LABELS` · `NOTIFY_ACTIONS` · `ACTION_LABELS`) · toast "ใบเบิกใหม่เข้า" ของ staff (realtime INSERT) อาจเด้งให้ใบที่ถูกถอนภายในไม่กี่วินาที → toast ตรวจว่ายังมีใบอยู่ก่อนพาไป หรือยอมรับ (ตัดสินตอนลงมือ)

## ทางเลือกที่ไม่เลือก

- **ตรวจยอดใน SQL ทั้งหมด (constraint/trigger)** — ปลอดภัยสุดในทางทฤษฎี แต่ต้องเขียน `parseUnit` + กฎจอง 6 สถานะ + `picked_allocation` ซ้ำใน plpgsql → 2 แหล่งความจริง · ทางไปต่อถ้าจำเป็น: เก็บ `pack_size` ต่อแถว inventory ตอนนำเข้า (คำนวณด้วย `parseUnitFactor` ตัวเดียว) + `reserved_base` ต่อรายการที่แอปเขียนทุกครั้งที่สถานะเปลี่ยน แล้ว SQL รวมเลขธรรมดาได้ — งานใหญ่ ทำเมื่อ insert-then-verify ไม่พอ
- **ล็อกตารางด้วย advisory lock** — PostgREST ถือ lock ข้าม request ไม่ได้ ต้องย้ายทั้ง read+check+insert เข้า RPC = กลับไปข้อบน
- **ไม่ทำอะไร (พึ่ง staff ตอนจัดยา)** — ผู้เบิกเห็น "ส่งสำเร็จ" ทั้งที่ของไม่พอ ขัดเป้าหมาย pilot

## Consequences

- **Positive:** ไม่มีใบเปล่า · จองเกินพร้อมกันเป็นไปไม่ได้ (พิสูจน์ข้างบน) · สูตรพร้อมเบิกยังอยู่ที่เดียว (JS)
- **Negative:** RPC ตัวแรกของ repo (ต้องมี migration `.sql` + บันทึกใน `docs/schema.md` + ระบุใน PR ว่าต้องรันก่อน deploy) · ส่งใบเบิกช้าขึ้น 1 รอบอ่าน (~0.2–1 วิ) · ใบที่ชนจริงอาจถูกถอนทั้งคู่
- **Risk:** ถ้าเบราว์เซอร์ปิดระหว่าง "บันทึกแล้ว" กับ "ตรวจซ้ำเสร็จ" ใบที่เกินยังค้าง (หน้าต่างแคบ) — staff ยังจับได้ตอนจัดยาเหมือนวันนี้

## แผนลงมือ + วิธีพิสูจน์ (ทำใน session ถัดไป เมื่อได้รับอนุญาต)

1. `/grill-with-docs` ยืนยัน 3 คำถาม: ถอนใบ = ลบ หรือสถานะใหม่ (ลบ = staff ไม่เห็น / สถานะ = ต้องแก้ทุกจุดที่ list สถานะ) · toast ของ staff · ข้อความถึงผู้เบิก
2. pure module `src/lib/reservationCheck.js` — `findOverReserved({ invBase, reserved, codes })` + golden test (`npm run test:reservecheck`) ครอบ: ไม่ชน · ชน 1 รหัส · packsize ต่างกัน · รหัสที่ไม่มีใน inventory · ยอดเท่ากันพอดี (ไม่ชน)
3. migration `requisition_submit_rpc_migration.sql` (`submit_requisition` + `withdraw_requisition`) — **รันบน Supabase จริงเมื่อ user สั่งเท่านั้น**
4. `db.js`: `submitRequisition(header, items, auth)` / `withdrawRequisition(id, auth)` — RequisitionApp เรียกแทน insert ตรง
5. **พิสูจน์การชน (ต้องเขียนข้อมูลจริง — ขออนุญาตก่อน):** สคริปต์ Playwright 2 context พร้อมกัน หน่วยงาน "ทดลองระบบ" รหัสยาที่คงเหลือน้อย ขอคนละเกินครึ่ง → ต้องได้ ≤ 1 ใบ · ลบใบทดสอบท้ายสคริปต์ · หรือใช้ Supabase branch ถ้ามี (MCP `create_branch` — ตรวจค่าใช้จ่ายก่อน)
6. mutation test: ปิดขั้นตรวจซ้ำ → สคริปต์ข้อ 5 ต้องได้ 2 ใบ (ยืนยันว่าเทสจับได้)
