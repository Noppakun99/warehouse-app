# 0012. ผูกนโยบายเปลี่ยน/คืนยากับบริษัทของ lot นั้นจริงๆ — ไม่เดา

- **Status:** Accepted (ส่วน *การผูก supplier ต่อ lot* ยังใช้อยู่; ส่วน *วิธีอ่านนโยบาย* "เฟส 1 ไม่ parse ตัวเลข" ถูก refine โดย [ADR-0014](0014-structured-return-policy-tier-percent.md) — เฟส 2 อ่าน structured tier %)
- **Date:** 2026-07-12

## Context

ยา 1 รหัส (`drug_code`) อาจถูกซื้อจาก **หลายบริษัทต่างช่วงเวลา** — จากข้อมูลจริง **≈23% ของรหัสยา (95/415)** มี `supplier_current` มากกว่า 1 บริษัทใน `receive_logs`.

นโยบายการรับเปลี่ยน/คืนยา (`drug_swap_policy`) เป็นข้อตกลง **รายบริษัท** และการคืนจริง **คืนได้กับบริษัทที่ขาย lot นั้นเท่านั้น** — คืนข้ามเจ้าไม่ได้. ระบบใช้ค่านี้คำนวณ [[deadline เปลี่ยนยา]] = `exp − จำนวนเดือนตามนโยบาย` เพื่อเตือน staff ให้คืนทันก่อนเสียสิทธิ์.

โค้ดเดิม (2 path: popup Dashboard `fetchSwapReturnDue` และ modal แผนผัง `buildReturnInfo`) ผูกนโยบายที่ระดับ **รหัสยา** โดยหยิบ **บริษัทล่าสุดของรหัส** (หรือแถวแรก arbitrary เมื่อ match lot ไม่ได้). ผลคือ lot ที่ซื้อจากบริษัท A ถูกคำนวณ deadline ด้วยนโยบายของบริษัท B (บริษัทล่าสุด) — เช่น lot ที่ซื้อจากภิญโญ (นโยบาย "แล้วแต่รายการ") ถูกตีด้วยนโยบายแอตแลนติค (คืนภายใน 12 เดือน) → แสดง deadline ที่ไม่มีอยู่จริง และชี้ให้คืนผิดบริษัท.

มี edge เพิ่มอีก 2 แบบจากข้อมูลจริง: (1) lot ใน inventory ที่ **ไม่มีแถว match ใน `receive_logs`**; (2) `code+lot` เดียวกันถูกรับจาก **2 บริษัท** (พบ 2 เคส — เพราะเลข lot บริษัทตั้งเอง ชนกันได้).

## Decision

นโยบายเปลี่ยน/คืนยาของแต่ละ lot **ผูกกับบริษัทที่ส่ง lot นั้นจริงๆ** โดย match `drug_code` + `lot` ให้ตรงแถวใน `receive_logs`:

- **match ได้ 1 บริษัท (unique)** → ใช้ supplier + นโยบายของแถวนั้นคำนวณ deadline.
- **ไม่มีแถว match** → **ไม่แสดง deadline**.
- **`code+lot` ชนหลายบริษัท** → **ไม่แสดง deadline** (กำกวมว่าคืนเจ้าไหน).

รวมเป็นกฎเดียว: **supplier ต่อ `code|lot` ต้อง unique เท่านั้นจึงคำนวณ deadline** — ไม่ unique หรือไม่มี = เงียบ. **ห้าม fallback ไปแถวอื่นของรหัสเดียวกัน.**

## Consequences

- Positive: deadline ตรงกับบริษัทเจ้าของ lot จริง — ไม่ชี้คืนผิดเจ้า, ไม่สร้าง deadline ปลอมสำหรับ lot ที่บริษัทจริงไม่มีนโยบายคืน.
- Positive: กฎ "unique เท่านั้น" ทำให้ 3 กรณีเสี่ยง (ไม่เจอ / ชน / ต่างรายการ) fail-safe ทางเดียวกัน — อ่านง่าย.
- Negative / trade-off: **ยอมพลาดการเตือน** สำหรับ lot ที่ match ไม่ได้ (เช่น lot เก่าที่ import inventory มาโดยไม่มีบิลรับใน `receive_logs`) — เลือก "เตือนขาด" ดีกว่า "เตือนผิดบริษัท" เพราะการคืนผิดเจ้าเสียเวลาจริงและทำให้ไม่เชื่อระบบ.
- Follow-ups / risks: ถ้าอนาคตต้องการครอบ lot ที่ match ไม่ได้ ต้องเพิ่มแหล่ง supplier-per-lot ที่เชื่อถือได้ (เช่น เก็บ supplier ลง `inventory` ตอน import) ไม่ใช่เดาจากบริษัทล่าสุด. Coverage ([[ความจำเป็นต้องคืน]]) ยังคิดต่อรหัสยาเหมือนเดิม — เปลี่ยนแค่การผูก supplier/policy ต่อ lot.

## Alternatives considered

- **ผูกบริษัทล่าสุดของรหัส (เดิม)** — ง่าย แต่ผิดสำหรับ 23% ของรหัสที่มีหลายบริษัท: คำนวณ deadline ด้วยนโยบายบริษัทที่ไม่ได้ขาย lot นั้น → คืนผิดเจ้า / deadline ปลอม.
- **lot ชน/ไม่เจอ → fallback ใช้บริษัทล่าสุด + ติดป้าย "ประมาณ"** — ยังเสี่ยงชี้คืนผิดเจ้า และป้ายเตือนมักถูกมองข้าม; ขัดหลัก "ไม่เดาเรื่องการคืนเงิน/สิทธิ์".
- **เก็บ supplier ต่อ lot ลง `inventory` ตอน import** — แก้รากที่สุด(ครอบ lot ที่ไม่มีใน receive_logs ด้วย) แต่กระทบ pipeline import + schema; เกินขอบเขตรอบนี้ เก็บเป็น follow-up.
