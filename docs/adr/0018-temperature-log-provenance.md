# ADR-0018: อุณหภูมิตู้เย็น — เก็บที่มาของค่า (provenance) แทนการลบค่าที่ไม่ได้วัดจริง

วันที่: 2026-08-16
สถานะ: ยอมรับ (accepted)

## บริบท

คลังยาบันทึกอุณหภูมิตู้เย็นเก็บยา (1 ตู้) ผ่าน Google Form ตั้งแต่ พ.ค. 2025 กำลังย้ายเข้าแอป

ตรวจสอบข้อมูลต้นทาง (2026-08-16) พบว่า **ข้อมูลส่วนใหญ่ไม่ได้มาจากการวัดจริง** — Apps Script
ชื่อ `Tempตู้เย็น` มีฟังก์ชัน `autoFillTemperature` ที่ตั้ง time-based trigger รันทุกวัน แล้ว:

```javascript
var temp9  = (Math.random() * (8 - 2) + 2).toFixed(1);
var temp15 = (Math.random() * (8 - 2) + 2).toFixed(1);
sheet.appendRow([new Date(), dateOnly, "09:00 น.", temp9,  "เก้า"]);
sheet.appendRow([new Date(), dateOnly, "15:00 น.", temp15, "เก้า"]);
```

สุ่มค่าในช่วง 2–8 ซึ่ง**คือช่วงที่ผ่านเกณฑ์พอดี** จึงไม่มีวันหลุดช่วง — เจตนาเดิมคือ
"เจ้าหน้าที่ลืมมาบันทึก ก็ให้ระบบ make ขึ้นไว้" (ยืนยันโดยผู้ใช้)

ข้อมูลจึงแบ่งเป็น 3 ชุด:

| ชุด | ช่วง | ที่มา | ประมาณ |
|---|---|---|---|
| A | 13/06/2025–15/07/2025 + วันที่ P'Jeab/K/ไนท์ กรอก | คนวัดจริง | ~50 แถว |
| B | 17/02/2026–15/08/2026 (timestamp `21:35:5x`) | `Math.random()` | ~350 แถว |
| C | 01/05/2025–12/06/2025 (ค่านิ่ง 2.2–2.5) | คนวัดจริง (ผู้ใช้ยืนยัน) | ~60 แถว |

คำถามที่ต้องตัดสิน: **ชุด B ทำอย่างไร** — ทิ้ง, import ปกติ, หรืออย่างอื่น?

## การตัดสินใจ

### 1. ปิด trigger ทันที (ทำแล้ว 2026-08-16)

ลบ trigger `autoFillTemperature` ออกจาก Apps Script — ทุกวันที่ปล่อยไว้คือข้อมูลปลอมเพิ่ม 2 แถว
(เมนู Apps Script มีแต่ "Delete trigger" ไม่มี "ปิดชั่วคราว" — โค้ดฟังก์ชันยังอยู่ในไฟล์)

### 2. import ชุด B แต่**ติดธงที่มา** ไม่ลบทิ้ง

`temperature_log.source` เก็บที่มาของทุกแถว:

| ค่า | ความหมาย |
|---|---|
| `manual` | คนกรอกผ่านแอป (ค่าเริ่มต้นของการบันทึกใหม่) |
| `form_import` | ย้ายมาจาก Google Form — คนวัดจริง (ชุด A, C) |
| `generated` | **ค่าที่ระบบสุ่มขึ้น ไม่ใช่การวัดจริง** (ชุด B) |
| `device` | อุปกรณ์ data logger ส่ง/import เข้ามา (รองรับอนาคต) |

**เหตุผลที่ไม่ลบทิ้ง:** การลบทำให้ประวัติ "ดูดี" แต่ปิดบังว่าเคยเกิดอะไรขึ้น —
ถ้าวันหน้ามีคนถามว่า "ทำไม ก.พ.–ส.ค. 2026 ไม่มีข้อมูล" จะไม่มีคำตอบ
เก็บไว้พร้อมธงตอบได้ว่า *"ช่วงนั้นไม่มีการวัดจริง และนี่คือหลักฐาน"*
ตรงกับหลัก append-only ของ [ADR-0008](0008-stock-count-append-only-snapshot.md)

**เหตุผลที่ไม่ import ปกติ:** ค่าสุ่มปนกับค่าจริงโดยแยกไม่ออก = หลักฐานเท็จในเวชระเบียน
ซึ่งในมุมผู้ตรวจ GDP/HA ร้ายแรงกว่า "ลืมจด"

### 3. `generated` ต้องถูกตัดออกจากทุกการคำนวณ — ไม่ใช่แค่ทำสีเทา

แถว `source='generated'` **ห้ามเข้า**: สถิติ (min/max/avg), กราฟแนวโน้ม, การนับ%ความครบถ้วน,
การตรวจจับ excursion, และ **Excel export ต้องมีคอลัมน์ "ที่มา" ติดไปด้วยเสมอ**

แสดงในตารางประวัติได้ (เพื่อ audit trail) แต่ต้องมีป้ายกำกับชัดว่าไม่ใช่ค่าจริง

### 4. ⛔ ไม่ทำตาราง `temperature_point` (จุดวัด) ในเฟสนี้

มีตู้เดียว คลังดูแลเอง (ยืนยันโดยผู้ใช้) — เก็บ `location` เป็น TEXT ในแถว
ถ้าวันหน้ามีตู้ที่ 2 ค่อยแยกตารางทีหลัง ยังไม่จ่ายค่า abstraction ตอนนี้

**แต่เก็บเกณฑ์ช่วงยอมรับ (`min_c`/`max_c`) ไว้ในแถวทุกแถว** ไม่ hardcode 2–8 ในโค้ด —
เพราะถ้าตู้ที่ 2 เป็นตู้แช่แข็ง (−20°C) เกณฑ์จะต่างกัน และค่าที่บันทึกไว้แล้ว
ต้องคงเกณฑ์ ณ เวลานั้นไว้ (แบบเดียวกับ snapshot ของ [ADR-0008](0008-stock-count-append-only-snapshot.md))

### 5. เพิ่มการบันทึก "การดำเนินการเมื่อหลุดช่วง" (corrective action)

ฟอร์มเดิมไม่มีช่องนี้ — ผู้ใช้ยืนยันว่า "บันทึกไว้อย่างเดียว ไม่ได้ทำอะไร"
ซึ่งเป็นช่องว่างที่ผู้ตรวจ GDP/HA ถามหา

เก็บ `action_taken` (TEXT) ในแถวเดียวกัน ไม่แยกตาราง — เพราะ 1 excursion = 1 การอ่านค่า
ไม่มีความสัมพันธ์ 1-ต่อ-หลาย

### 6. เก็บ "อุปกรณ์ที่ใช้วัด" (`device`) แยกจาก `source`

`source` ตอบว่า *ข้อมูลมาจากไหน* (คนกรอก/import/สุ่ม) — แต่ไม่ตอบว่า *วัดด้วยอะไร*

เพิ่ม `device`: `fridge_display` | `thermometer` | `data_logger` | `none`

**เหตุผล:** ผู้ใช้ยืนยัน (2026-08-16) ว่า **ปัจจุบันไม่มีเครื่องวัดแยก — อ่านค่าจากจอของตู้เย็นเอง**
ซึ่งเป็นข้อมูลที่เปลี่ยนความหมายของตัวเลขทั้งชุด: จอตู้วัด**อากาศใกล้คอยล์ ไม่ใช่อุณหภูมิของยา**
และ**ไม่มีใบสอบเทียบ** → ใช้ดูแนวโน้ม/จับเหตุตู้เสียได้ แต่ยืนยันกับผู้ตรวจ GDP/HA ไม่ได้

ค่าเดิม 115 แถว backfill เป็น `fridge_display` ทั้งหมด (ผู้ใช้ยืนยันว่าอ่านจากจอตู้มาตลอด);
`generated` → `device='none'` เพราะไม่ได้วัดด้วยอะไรเลย

UI เตือนใต้ dropdown เมื่อเลือก `fridge_display` — ไม่บล็อกการบันทึก เพราะนี่คือสภาพจริง
ที่ต้องใช้งานต่อ แต่ผู้ใช้ต้องรู้ข้อจำกัด

### 7. "ไม่ได้บันทึก" = แถวที่ไม่มีอยู่ ไม่ใช่แถวที่มีค่าพิเศษ

ไม่สร้างแถว placeholder สำหรับรอบที่ไม่มีคนวัด — ความครบถ้วนคำนวณจาก
*จำนวนแถวจริง ÷ จำนวนรอบที่ควรมี* แล้วแสดงเป็น % (เช่น "บันทึกครบ 52/62 รอบ = 84%")

**เหตุผล:** ถ้าสร้างแถวว่างไว้ จะกลายเป็นที่ให้คนมา "เติมย้อนหลัง" ซึ่งคือปัญหาเดิมที่เพิ่งแก้

## ผลที่ตามมา

**ได้:**
- แยกค่าจริงกับค่าปลอมออกจากกันถาวร — สถิติที่แสดงเชื่อถือได้
- เก็บหลักฐานว่าเคยเกิดอะไรขึ้น ตอบผู้ตรวจได้
- % ความครบถ้วนเป็นตัวเลขจริงที่กดดันให้เกิดการวัดจริง แทนการเติมให้ครบปลอมๆ
- รองรับ data logger ในอนาคตโดยไม่ต้องแก้ schema (`source='device'`)

**เสีย:**
- ทุกจุดที่ query ต้องจำ filter `source <> 'generated'` — ถ้าลืมจุดเดียว สถิติเพี้ยนทันที
  (บรรเทาด้วยการรวม filter ไว้ใน `db.js` ชั้นเดียว ไม่ให้ component ประกอบ query เอง)
- กราฟจะมีช่วงว่างยาว (ก.ค. 2025–ม.ค. 2026 + ช่วงที่เป็น generated) ซึ่ง**ตั้งใจให้เห็น**

## ทางเลือกที่ปฏิเสธ

**ลบชุด B ทิ้ง** — สะอาดกว่า แต่ทำลายหลักฐาน ผู้ใช้เลือกเก็บไว้แบบติดธง

**ให้ trigger เติมค่าต่อแต่ติดธง** — ยังเป็นการสร้างข้อมูลที่ไม่ได้วัด ไม่แก้ปัญหาต้นเหตุ
(ปัญหาคือ "ลืมวัด" ไม่ใช่ "ตารางมีช่องว่าง") — แก้ด้วยการเตือนก่อนหมดเวรแทน

**ทำ `temperature_point` ตั้งแต่แรก** — over-engineering สำหรับตู้เดียว
