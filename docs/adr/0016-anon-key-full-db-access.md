# ADR-0016: anon key เข้าถึง DB ได้เต็มสิทธิ์ — ความเสี่ยงที่ยอมรับไว้ชั่วคราว

## สถานะ
Accepted (บันทึกสถานะปัจจุบัน + ยอมรับความเสี่ยงชั่วคราว) — 2026-08-13
**ทางแก้ยังไม่เลือก** — ดู §ทางเลือก

## บริบท

ระบบใช้ auth ของตัวเอง (username + SHA-256 เก็บใน `app_users`) **ไม่ใช่ Supabase Auth** — ดู [docs/auth.md](../auth.md). ผลคือ RLS ไม่มีทางรู้ว่า request มาจากใคร เพราะ Postgres เห็นทุก request เป็น role `anon` เหมือนกันหมด

เพื่อให้แอปทำงานได้ ทุกตารางจึงได้ policy เปิดกว้างเหมือนกันหมด:

```sql
CREATE POLICY "Allow public all" ON <table>
  FOR ALL TO public USING (true) WITH CHECK (true);
```

**RLS เปิดอยู่ก็จริง แต่ policy อนุญาตทุกอย่างกับทุกคน = ป้องกันได้ศูนย์**

### สิ่งที่วัดได้จริง (ตรวจผ่าน Supabase MCP 2026-08-13)

| | |
|---|---|
| ตารางใน `public` | 23 |
| ตารางที่มี policy `FOR ALL USING(true)` | **21** (ทุกตารางของแอป) |
| `has_table_privilege('anon', …)` | **SELECT / INSERT / UPDATE / DELETE = true ทั้ง 23 ตาราง** |
| ตาราง backup ที่ RLS ปิดสนิท | 2 → **ปิดแล้ว** 2026-08-13 (`ENABLE RLS` ไม่ใส่ policy) |

`VITE_SUPABASE_ANON_KEY` เป็น build-time env ของ Vite → **ฝังอยู่ใน bundle ที่ browser ดาวน์โหลด** ใครเปิดเว็บก็อ่านค่าได้จาก DevTools

### ผลที่ตามมา

ใครก็ตามที่มี anon key ยิง PostgREST ตรงได้โดย **ไม่ต้องผ่านหน้า login เลย** (login เป็น logic ฝั่ง client ล้วน — `loginUser` ใน [db.js](../../src/lib/db.js) แค่ SELECT แล้วเทียบ hash ใน browser):

- **`app_users` (13 แถว)** — อ่าน `password_hash` ได้ทั้งตาราง; hash เป็น **SHA-256 ไม่มี salt ไม่มี iteration** ([db.js:1499-1502](../../src/lib/db.js#L1499-L1502)) → rainbow table ถอดรหัสผ่านที่คาดเดาง่ายได้ทันที. แก้ `role` ตัวเองเป็น `admin` ก็ได้ หรือ INSERT user ใหม่เข้าไปเลย
- **`dispense_logs` (6,905) · `receive_logs` (2,632) · `stock_ledger` (2,885) · `inventory` (879)** — อ่าน/แก้/ลบได้หมด รวมงวดบัญชีที่ปิดแล้ว (ADR-0007 freeze ที่ชั้น app ไม่ใช่ชั้น DB)
- **`audit_logs` (1,639)** — เขียนได้ **และลบได้** → ผู้บุกรุกลบร่องรอยตัวเองได้ ทำให้ audit trail ไม่น่าเชื่อถือในเชิงนิติวิทยาศาสตร์
- `registerUser` ยัง `SELECT password_hash` ทั้งตารางมาเช็ครหัสผ่านซ้ำ ([db.js:1558](../../src/lib/db.js#L1558)) — ทำให้ hash ทั้งชุดวิ่งผ่าน client ตามปกติของแอปเองด้วย

**นี่ไม่ใช่บั๊กจุดเดียว** แต่เป็นผลตรงของการเลือก custom auth — สอดคล้องกันทั้งระบบ และแก้ทีละจุดไม่ได้

## การตัดสินใจ

**ยอมรับความเสี่ยงนี้ต่อไปก่อน** และบันทึกไว้ให้ชัดว่าเป็นการเลือกที่รู้ตัว ไม่ใช่ความพลาดที่มองข้าม พร้อมกฎ 2 ข้อระหว่างที่ยังไม่แก้:

1. **ตารางใหม่ที่ไม่มีโค้ด client เรียกใช้ ต้อง `ENABLE ROW LEVEL SECURITY` โดยไม่ใส่ policy** — เช่น ตาราง backup/staging. ปิดสนิทจาก client เหลือเฉพาะ service_role และ SQL Editor (ทำกับ `_bak_inventory_ss_20260704` / `_bak_inventory_lot_20260731` แล้ว)
2. **ห้ามใส่ข้อมูลที่ระบุตัวผู้ป่วยลง Supabase** — ตราบใดที่ยังเปิดกว้างแบบนี้ ขอบเขตความเสียหายต้องจำกัดอยู่ที่ข้อมูลคลังยาและบัญชีผู้ใช้ในระบบเท่านั้น

**เหตุผลที่ยังไม่แก้ตอนนี้:** ทางแก้ทุกทางแตะ auth ซึ่งเป็นหัวใจของทุก sub-app — เป็นงานระดับสัปดาห์ ไม่ใช่ patch และการแก้ผิดครึ่งๆ กลางๆ (เช่น เขียน RLS policy จำกัดสิทธิ์โดยที่ Postgres ยังไม่รู้จักผู้ใช้) จะทำให้ **แอปพังทั้งระบบทันที** ต้องวางแผนก่อน

## ทางเลือก

เรียงจากงานน้อย→มาก ทุกทางต้อง `REVOKE` สิทธิ์ `anon` ที่ไม่จำเป็นออกเป็นขั้นสุดท้าย

### A. ปิดเฉพาะ `app_users` ก่อน (แนะนำเป็นก้าวแรก)
ย้าย login/สมัคร/เปลี่ยนรหัสไปอยู่หลัง Edge Function ที่ถือ `service_role` แล้ว `REVOKE ALL ON app_users FROM anon`

- **ได้**: hash รหัสผ่านออกจากมือ client ทันที — ปิดช่องที่อันตรายที่สุด (ยกระดับสิทธิ์ตัวเองเป็น admin)
- **เสีย**: ต้องแก้ `loginUser`/`registerUser`/`UserManagementApp` + deploy edge function เพิ่ม
- **ขอบเขต**: จำกัด ไม่แตะ sub-app อื่นเลย

### B. ย้าย mutation ทั้งหมดไปหลัง Edge Function
client เหลือสิทธิ์ SELECT, ทุก INSERT/UPDATE/DELETE ผ่าน function ที่ตรวจ session เอง

- **ได้**: ข้อมูลแก้ไม่ได้จากภายนอก, audit log เชื่อถือได้จริง
- **เสีย**: ต้องเขียน endpoint ครอบ mutation แทบทุกตัวใน `db.js` — งานใหญ่ และเพิ่ม latency
- **ขอบเขต**: ทั้งระบบ

### C. ย้ายไป Supabase Auth เต็มตัว
เลิก `app_users` + hash เอง แล้วใช้ `auth.users` + RLS ที่อ้าง `auth.uid()` / custom claim สำหรับ role

- **ได้**: ถูกหลักที่สุด — DB บังคับสิทธิ์เอง ไม่ต้องเชื่อ client, ได้ password hashing/reset/rate-limit ฟรี
- **เสีย**: ต้อง migrate ผู้ใช้ 13 คน (บังคับตั้งรหัสใหม่ เพราะ SHA-256 ไม่มี salt ย้ายเข้า bcrypt ตรงๆ ไม่ได้), เขียน policy ใหม่ทั้ง 21 ตาราง, แก้ระบบสิทธิ์รายคน (Critical Rule #23) ให้ผูกกับ claim
- **ขอบเขต**: ทั้งระบบ + ต้องประสานกับผู้ใช้จริง

### D. คงสภาพเดิมถาวร
ยอมรับว่าใครมี URL ก็เข้าถึงข้อมูลได้ทั้งหมด

- **ปฏิเสธ** — เว็บ deploy บน Netlify เข้าถึงได้จากอินเทอร์เน็ตสาธารณะ ไม่ได้จำกัดอยู่ในเครือข่ายโรงพยาบาล ([docs/deployment.md](../deployment.md)) ความเสี่ยงจึงไม่ได้ถูกจำกัดด้วยสภาพแวดล้อม

## ผลกระทบ

- ตาราง backup 2 ตัวปิดจาก client แล้ว (2026-08-13) — ตรวจว่าไม่มีโค้ดเรียกใช้ก่อนปิด ไม่กระทบแอป
- ตารางแอปอีก 21 ตัว **ยังเปิดกว้างเหมือนเดิม** — สถานะไม่เปลี่ยนจากก่อนหน้า ADR นี้
- ก่อนเพิ่มข้อมูลประเภทใหม่ (โดยเฉพาะข้อมูลบุคคล) ต้องกลับมาอ่าน ADR นี้ก่อน
