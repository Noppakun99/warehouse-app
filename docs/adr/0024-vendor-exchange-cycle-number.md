# ADR-0024: คลังออก "เลขที่รอบ" เองเพื่อผูกขาออกกับขาเข้าของรอบเปลี่ยนคืนบริษัท

วันที่: 2026-09-07 · สถานะ: **ยอมรับ** · เกี่ยวข้อง: [ADR-0012](0012-swap-return-policy-per-lot-supplier.md) · [ADR-0014](0014-structured-return-policy-tier-percent.md)

## บริบท

คลังส่งยาที่มีปัญหา (ใกล้หมดอายุ / บริษัทเรียกเก็บ / คุณภาพ) คืนบริษัทแล้วรอของเปลี่ยนกลับ
ระหว่างนั้นของถูกหักออกจากคลังแล้วแต่ยังไม่ได้ของคืน — เรียกว่า **"ของลอย"**

สภาพจริงที่ตรวจจากไฟล์ CSV ของคลังแล้ว:

- **บริษัทส่วนใหญ่ไม่ออกเอกสารให้** ผู้แทนเดินมาเก็บของที่คลังแล้วไปเลย คลังต้องเขียนกระดาษเองเป็น
  หลักฐานชิ้นเดียวที่ยืนยันว่าของออกไปเมื่อไหร่ (บริษัทใหญ่อย่าง Zuellig มี RMA เป็นข้อยกเว้น)
- **สองขาบันทึกคนละตาราง ไม่มี key ผูกกัน** — ขาออกอยู่ในไฟล์เบิก (`ชนิดรายการ` = แลกเปลี่ยนยา/คืนยา)
  ขาเข้าอยู่ในไฟล์รับ (`สถานะการซื้อ` = แลกเปลี่ยนยา) ความเชื่อมโยงมีอยู่บนกระดาษเท่านั้น ไม่รอดเข้าระบบ
- **lot เปลี่ยนระหว่างทางเสมอ** (ส่ง `NP26099A` → ได้ `NP26101A` คืน) จับคู่ด้วย lot ไม่ได้
- **52% ของขาเข้าเป็นยาคนละรหัสกับที่ส่งไป** (14 จาก 27 แถว) — ของชดเชยคนละตัว เช่น ABCA คืน
  Lidocaine Viscous แล้วได้ Racser Viscous มาแทน จับคู่ด้วยรหัสยาก็ไม่ได้
- **จำนวนไม่เท่ากัน** — Omeprazole ส่งออกรวม 847 รับกลับ 1,447 · Enalapril ส่ง 37 รับ 80
- ความเชื่อมโยงที่มีอยู่ถูกเขียนเป็นภาษาคนในช่องหมายเหตุ ระบบอ่านไม่ได้ เช่น
  `"ทดแทนของเดิม 23กล่อง45แผง Lot 26D212 ที่คืนบริษัท"` · `"ได้ยาแล้ว 100"`
- ผลคือ `vendorExchange.js` ต้อง **เดา** คู่จาก รหัสยา + บริษัท + ลำดับเวลา และเขียนคำเตือนไว้เองว่า
  *"ไม่มี key ผูก 2 ขาในข้อมูลต้นทาง ... ผู้ใช้ต้อง verify กับเอกสารจริง"*
- เคสล่าสุด (Salbutamol + Aspirin ส่ง 14/8 กลับ 2/9) ขาเข้า **ไม่เคยถูกบันทึกเลย** ทั้งที่กระดาษเซ็นครบ
  ระบบจึงยังคิดว่าของลอยอยู่ทั้งที่กลับมาแล้ว

## การตัดสินใจ

**คลังออก "เลขที่รอบ" ของตัวเอง** รูปแบบ `VX-<ปีพ.ศ. 2 หลัก><เดือน 2 หลัก>-<ลำดับ>` (เช่น `VX-6909-001`)
เขียนบนใบส่งคืนตอนผู้แทนมารับของ และใบรับกลับอ้างเลขเดิมเมื่อของกลับมา

เมื่อบันทึกเข้าระบบ เลขนี้ถูกเขียนลง:

- **ขาออก** → ช่องหมายเหตุของไฟล์เบิก
- **ขาเข้า** → **ช่องเลขที่บิล** ของไฟล์รับ

`vendorExchange.js` จับคู่ **2 ชั้น**: ชั้นแรกใช้เลขรอบ (ตรงกัน = คู่กันแน่นอน ไม่สนรหัสยา/บริษัท/ลำดับเวลา
เพราะเอกสารยืนยันแล้ว) ชั้นสองจึงค่อยเดาแบบเดิมสำหรับรอบเก่าที่ไม่มีเลข ผลลัพธ์ติดธง `matchedBy`
เป็น `'vx'` (ยืนยันจากเอกสาร) หรือ `'guess'` (อนุมานเอง)

**เลือกช่องเลขที่บิลเป็นที่เก็บฝั่งขาเข้า ไม่สร้างคอลัมน์ใหม่** เพราะคลังใช้ช่องนี้เขียน "อ้างอิงอะไรสักอย่าง"
อยู่แล้วเมื่อไม่มีเลขบิลจริง — พบค่าอย่าง `ใบคืนยา` · `ใบยืมยา/คืนยา` · `แบบฟอร์มใบยืม-คืนสินค้า` ·
`เปลี่ยนเวชภัณฑ์ยา ชดเชยสินค้า` การใส่เลขรอบจึงเป็นการทำสิ่งที่ทำอยู่แล้วให้เป็นระบบ ไม่ใช่งานใหม่

## ผลที่ตามมา

- **บวก** — การเชื่อม 2 ขากลายเป็น *ข้อเท็จจริงที่คนเขียนไว้* แทน *ผลการเดาของอัลกอริทึม*
  `vendorExchange.js` เลิกเป็น "ตัวช่วยเตือน" กลายเป็นทะเบียนที่เชื่อได้สำหรับรอบที่มีเลข
- **บวก** — จับคู่ได้แม้ **ของที่ได้คืนเป็นยาคนละตัว** ซึ่งชั้นเดาทำไม่ได้เลย และเป็นเคสส่วนใหญ่ (52%)
- **บวก** — ไม่ต้องแก้ schema ไม่ต้อง migration ใช้ช่องที่มีอยู่แล้ว
- **บวก** — เข้ากันได้กับข้อมูลเก่า รอบก่อนหน้ายังจับคู่ด้วยวิธีเดิม `guessMatchedCount` บอกว่าเหลือ
  เท่าไรที่ยังต้อง verify กับกระดาษ
- **ลบ / สิ่งที่ยอมแลก** — **พึ่งวินัยคน** ถ้าไม่เขียนเลขบนกระดาษ หรือเขียนแล้วไม่ลงระบบ ก็ตกกลับไปเดา
  เหมือนเดิม ระบบไม่มีทางบังคับได้เพราะจุดกำเนิดคือกระดาษที่คลังเขียนเอง
- **ลบ** — เลขซ้ำได้ถ้าคนออกเลขชนกัน ไม่มีตัวกันที่ระบบ (ยังไม่มีทะเบียนรอบใน DB — ถ้าทำภายหลัง
  จะออกเลขให้อัตโนมัติได้ และดึงรายการขาออกมาเติมใบรับกลับให้เลย)
- **ลบ** — ช่องเลขที่บิลถูกใช้ 2 ความหมาย (เลขบิลจริง กับ เลขรอบภายใน) ต้องอ่านด้วย `parseVxNo`
  ไม่ใช่เทียบตรงๆ

## ทางเลือกที่พิจารณาแล้วไม่เลือก

- **ใช้เลขเอกสารของบริษัท (RMA)** — บริษัทส่วนใหญ่ไม่ออกเอกสาร มีแค่รายใหญ่ ใช้เป็น key หลักไม่ได้
  (แต่ฟอร์มมีช่องให้จดไว้ด้วย เพื่อใช้ตอบกลับเวลาบริษัททวงถามด้วยเลขของเขา)
- **สร้างคอลัมน์ใหม่ใน `receive_logs`** — ต้อง migration + แก้ทางนำเข้า CSV ทั้งเส้น ขณะที่ช่องเลขที่บิล
  ทำงานได้ทันทีและตรงกับพฤติกรรมที่คลังทำอยู่แล้ว
- **จับคู่ย้อนหลังในแอปโดยให้คนกดเลือก** — ยังต้องเดาก่อนเสนอ และแก้ปัญหาที่ปลายทาง ไม่ใช่ที่ต้นเหตุ
  (ต้นเหตุคือกระดาษไม่เคยพก key มาด้วย)
