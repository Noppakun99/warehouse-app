# ADR-0017: ตรวจนับคงคลัง — สถานะติดตามส่วนต่าง ระดับ "รายการ"

วันที่: 2026-08-16
สถานะ: ยอมรับ (accepted)

## บริบท

[ADR-0008](0008-stock-count-append-only-snapshot.md) ตัดสินว่าตรวจนับเป็น **append-only**: ระบบหา discrepancy ให้เห็น
แต่ **ไม่ปิด loop ให้** — "ส่วนต่างที่พบ ต้องมีคนตามแก้ที่ต้นทางเอง"

ใช้งานจริงมาถึงจุดที่ loop ที่ไม่ปิดกลายเป็นปัญหา: ประวัติมี 23 รอบ / 24 รายการไม่ตรง
แต่**ไม่มีใครรู้ว่ารายการไหนตามเรื่องแล้ว รายการไหนยังค้าง** — หัวหน้าคลังต้องไล่เปิดทีละรอบแล้วจำเอง

คำถามที่ต้องตัดสิน: เก็บสถานะติดตามที่ **ระดับรอบ (session)** หรือ **ระดับรายการ (item)**?

## การตัดสินใจ

### 1. เก็บที่ระดับ "รายการ" (`stock_count_item`)

เพิ่ม 4 คอลัมน์: `followup_status` / `followup_by` / `followup_at` / `followup_note`

**เหตุผล — รอบเดียวจบได้หลายทางพร้อมกัน.** ถามผู้ใช้ว่า "เจอระบบ 100 ของจริง 90 แล้วทำอะไรต่อ"
คำตอบคือ **"ทั้งสองแบบ แล้วแต่กรณี"** (บางเคสไปแก้ HosXP บางเคสแค่กรอกผิด)
รอบที่มี 6 lot ไม่ตรง 3 lot จึงมีได้ทั้ง 2 แบบปนกัน — ถ้าเก็บที่ระดับรอบจะบันทึกได้แค่แบบเดียว
และแยกไม่ออกว่า lot ไหนเคลียร์แล้ว

### 2. สถานะ 4 ค่า — สะท้อนทางจบจริง ไม่ใช่แค่ done/not-done

| ค่า | ความหมาย |
|---|---|
| `pending` | ยังไม่มีใครจัดการ (default — แถวเก่าทั้ง 90 แถวเป็นค่านี้) |
| `fixed_source` | ไปแก้ที่ต้นทางแล้ว (HosXP/CSV) |
| `confirmed_diff` | ยืนยันว่าส่วนต่างเป็นจริง (ของหาย/ย้ายชั้น) รับทราบ ไม่ต้องแก้ |
| `fixed_entry` | กรอกผิดตอนนับ แก้ค่าในแอปแล้ว |

`confirmed_diff` สำคัญที่สุด — เป็นทางออกที่ทำให้ผู้ใช้ **ไม่ต้องบิดตัวเลขให้ตรง**เพื่อให้ badge เขียว

### 3. ⛔ ไม่บังคับให้ทุกรอบจบที่ "ตรงทั้งหมด"

ผู้ใช้ขอเดิมว่า *"กลุ่มที่ไม่ตรง ต้องให้ user เข้าแก้ไขให้ครบเป็นตรงทั้งหมด"* — ซักค้านแล้วพบว่าหมายถึง
**"ตรวจให้ครบ 3 มิติ"** ไม่ใช่ "ทำให้ตัวเลขเท่ากัน"

ถ้าตีความอีกแบบ (เขียนทับ `counted_* = system_*`) จะ**ทำลายจุดประสงค์ทั้งระบบ**:
ผู้ใช้จะกด "ถูกแล้ว" รัวๆ เพื่อให้เขียว → ส่วนต่างจริงหายจากระบบ ซึ่งเป็นสิ่งเดียวที่ระบบนี้มีไว้จับ
(โดยเฉพาะ phantom stock ที่ CONTEXT.md ระบุว่า "discrepancy มูลค่าสูง")

**สถานะติดตามจึงไม่แตะ `counted_*` / `system_*` / `match` เลย** — ส่วนต่างอยู่ครบตาม ADR-0008

### 4. สรุป + ตัวกรอง = derived ไม่ persist

แถบสรุป (รอบทั้งหมด / ไม่ตรง / ยังไม่จัดการ / ตรวจครบ-ตรง) และตัวกรอง 5 แบบ
**คำนวณสดจาก `allItems` ที่โหลดครบอยู่แล้ว** ไม่เพิ่มคอลัมน์ ไม่เพิ่ม query

ตัวเลขบนแถบสรุป **ยึดขอบเขตวันที่/คำค้นเดียวกับตาราง แต่ไม่ขึ้นกับปุ่มกรองสถานะ**
(Critical Rule #6) — ไม่งั้นกดกรองแล้วตัวเลขเปลี่ยนตาม กลายเป็นงูกินหาง

## ทางเลือกที่ไม่เลือก

- **ระดับรอบ (session)**: migration เล็กกว่า UI ง่ายกว่า แต่บันทึกได้แค่ทางจบเดียวต่อรอบ — ขัดกับ "แล้วแต่กรณี"
- **บังคับให้ตรงทั้งหมด**: กลับ decision ADR-0008 และลบหลักฐาน discrepancy — ปฏิเสธ (ดูข้อ 3)
- **สถานะ boolean (จัดการแล้ว/ยัง)**: แยกไม่ออกว่า "แก้ต้นทาง" กับ "ยืนยันของหายจริง" ซึ่งต่างกันมากในแง่บัญชี

## ผลที่ตามมา

- migration: `stock_count_followup_migration.sql` (4 คอลัมน์ + index) — รันแล้ว 2026-08-16 แถวเก่า 90 แถว = `pending`
- audit action ใหม่ `followup_stock_count` → เพิ่มใน `ACTION_LABELS` ([AuditLogApp](../../src/AuditLogApp.jsx)) แล้ว
  **ไม่เข้ากระดิ่ง** ตาม precedent ของ `update_stock_count`/`delete_stock_count` (มีแค่ `create_stock_count` ที่เข้า)
- `updateStockCountFollowup()` แยกจาก `updateStockCountItem()` โดยเจตนา — ตัวหลังแก้ผลนับแล้ว recompute match, ตัวใหม่แตะสถานะอย่างเดียว
- ยังไม่มีการบังคับ/แจ้งเตือนเมื่อ `pending` ค้างนาน — ถ้าต้องการต้องออกแบบเพิ่ม (เฟสถัดไป)
