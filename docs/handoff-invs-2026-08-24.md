## 3. กระบวนการคลัง INVS ที่สรุปได้ (จากคู่มือหน้า 60–93)

**คลังใหญ่:** ① รับจากขนส่ง → ② จ่ายด่วน + ปลดเปลื้อง → ③ รับเข้าคลัง (3 กรณี: มี PO / มีใบรับขนส่ง / ไม่มี PO) + บาร์โค้ด → ④ ยืนยันการจ่าย
**คลังย่อย (ตัดทิ้ง ไม่มีในบริบทนี้):** ⑤ ขอเบิก → ⑥ จ่ายออก → ⑦ รับคืน → ⑧ โอน + ปลดเปลื้องค้างจ่าย
**Master data ที่ INVS บังคับ:** หน่วยงาน 4 ประเภท · กรอบบัญชีต่อคลัง · ประเภทเบิกจ่าย · เหตุผลยาคืน · วันหยุดไทย · บัญชียาหลัก + TMT/NCD24

**รายละเอียดจ่ายด่วนที่ verify แล้ว (หน้า 62–63):** ฟอร์มจ่ายด่วนมีแค่ คลัง + รายการ + จำนวน **ไม่มีช่องเอกสารใดๆ** และผลคือ *ยอดคงคลังเพิ่มขึ้น* (ตั้งยอดชั่วคราวให้จ่ายออกได้โดยไม่ติดลบ) · ปลดเปลื้องบังคับให้รับเข้าคลังจริงโดย **ระบุ Lot + EXP ให้ตรงกับรายการจ่ายด่วน** แล้วล้างที่เมนู โอน → แผนโอน → จ่าย · คำว่า "กรรมการตรวจรับ / หนังสือตรวจรับ" โผล่เฉพาะขั้นรับเข้าคลัง (หน้า 70–71)

## 4. Roadmap ที่ตกลงกันแล้ว (เรียงตามลำดับที่จะทำ)

**ทางเลือกที่เลือก = C** (จาก 3 ทาง A/B/C ที่เสนอ): **normalize ตอน import + master/alias — ไม่แตะข้อมูลประวัติ ไม่ต้อง backup**

เหตุผลชี้ขาด: `dispense_logs` ถูก **DELETE ทั้งตาราง + INSERT ใหม่** ทุกครั้งที่ import CSV (`src/DispenseLogApp.jsx:425` (delete-all) / `:428` (insert)) → การ UPDATE ค่าเก่าจะหายทันทีที่ import รอบหน้า แต่ในทางกลับกัน การ normalize ที่ import แล้ว import ไฟล์ประวัติเดิมซ้ำ 1 ครั้ง = ล้างประวัติได้ฟรีโดยไม่ต้องเขียน SQL UPDATE

**สคีมา (ยุบจาก 4 คอลัมน์เหลือ 3 หลังรู้ว่ามีคลังเดียว):**
- `code` — **รหัสหน่วยงานที่ไม่เปลี่ยน** (เช่น `ER`, `OPD`) ใช้เป็นจุดยึดแทนชื่อไทย (INVS มี "รหัสหน่วยงาน" อยู่แล้ว §5.1 และ INV DataSet ต้องใช้) — **เพิ่มเข้ามาจากคำถามที่ 2 ในการซักค้าน ดู §6**
- `dept_type` — `main_store` (คลังยา) / `requester` (หน่วยเบิก) / `adjustment` (รายการปรับปรุง) — เผื่อ `sub_store` ไว้ในอนาคตแต่ยังไม่ seed ใคร · **อาจต้องมีค่าสำหรับ "กลุ่มที่ยุบมาแล้ว" เพิ่ม ดู §0 ข้อ 2**
- `location_type` — ในโรงพยาบาล / ปฐมภูมิ / ภายนอก (เป็นตัวกำหนด `dis_dept`)
- `dis_dept` — 1–4 ตามสเปกกระทรวง (1 = OPD+ER, 2 = IPD+WARD, 3 = รพ.สต., 4 = อื่นๆ)
- ตารางใหม่ `department_alias` (pattern เดียวกับ `drug_name_alias` — Critical Rule #21)

## 6. เซสชัน /grill-with-docs ที่ค้างกลางคัน

ซักค้านแผนข้อ 1 ทีละคำถาม — **ข้อ 1 ปิดแล้ว · ข้อ 2 ถามแล้วรอคำตอบ**

### คำถามที่ 1 — ✅ ปิดแล้ว (ตอบได้จากประวัติ git ไม่ต้องรบกวนผู้ใช้)

**ปัญหา:** `CONTEXT.md:129` เขียนว่า `หน่วยงานผู้เบิก` **Is not** `หน่วยงานที่คืน` — *"คนละ list, คนละ lifecycle"* ซึ่งขัดกับแผนที่จะยุบเป็น master เดียว

**หลักฐานที่ปิดคำถาม:** บรรทัดนั้นเขียนใน commit `6152e94` (ระบบเบิก B-base) และ ณ commit นั้น `RequisitionApp` **อ่านจากตาราง `departments` ใน DB อยู่แล้ว** ส่วน `ReturnApp` เป็น array hardcode 19 ค่า (เหมือนวันนี้เป๊ะ ไม่เคยถูกแตะ) → บรรทัดนั้น **บันทึกสภาพโค้ด ไม่ใช่กฎของโดเมน** และคำว่า "lifecycle" ยกให้ผิดคำนาม — สิ่งที่มี lifecycle คือ *ใบเบิก* (`pending → picking → dispensed`) กับ *ใบคืน* (`pending → received`) ไม่ใช่ *หน่วยงาน*

**ข้อสรุป:** ยุบเป็น master เดียวได้ โดยแยก `บริษัทยา / Supplier` ไว้นอก master (คง `VENDOR_LABEL` ใน ReturnApp)

**ร่าง glossary ที่จะเขียนแทน (ยังไม่ได้เขียนลงไฟล์ — ดูเหตุผลด้านล่าง):**
> ### หน่วยงาน (Department)
> หน่วยขององค์กรที่ทำธุรกรรมกับคลังยา — ชุดเดียวทั้งระบบ ต่างกันที่ **บทบาท** ในแต่ละเหตุการณ์ (ผู้เบิก / ผู้คืน) ไม่ใช่ต่างที่ตัวตน
> - **Is not:** บริษัทยา/คู่ค้า — `บริษัทยา / Supplier` ใน dropdown คืนยาเป็นคู่ค้า ไม่ใช่หน่วยงาน อยู่นอก master
> - **ไม่มี lifecycle** — สิ่งที่มีสถานะคือ [[สถานะใบเบิก]] และ [[สถานะคืนยา (Return Status)]] ไม่ใช่หน่วยงาน

⛔ **ยังไม่เขียนลง `CONTEXT.md` เพราะ peer session ถือ `M CONTEXT.md` ค้างและกำลังจะ commit** — เขียนทับตอนนี้จะถูกลากเข้า commit เขาหรือชนกัน **ให้เขียนหลัง peer commit เสร็จ**

### คำถามที่ 2 — ถามแล้ว รอคำตอบผู้ใช้

**ปัญหา:** [ReturnApp.jsx:108](src/ReturnApp.jsx#L108) `deptToSource()` match **ชื่อไทยแบบตรงตัว** (`dept === 'ER (ฉุกเฉิน)'`, `'OPD (ผู้ป่วยนอก)'`) → พอ tab ใหม่ให้ admin แก้ชื่อหน่วยงานได้ วันที่มีคนแก้เป็น `ER` เฉยๆ ฟังก์ชันจะคืน `ward` **เงียบๆ ไม่ error** แท็บ `er` หยุดนับข้อมูลใหม่ = บั๊กตัวเดิมที่ ADR-0003 เขียนมาแก้ (เรียกที่เดียว: `ReturnApp.jsx:497` → เก็บลง `return_logs.return_source` → ใช้กรองใน `db.js:792-796`)

**ที่แก้เองได้ ไม่ต้องถาม:** เพิ่ม **`code` ที่ไม่เปลี่ยน** ในตาราง master (เช่น `ER`, `OPD`) แล้วให้ `deptToSource` match ที่ `code` — INVS มี "รหัสหน่วยงาน" อยู่แล้ว (คู่มือ §5.1) และ INV DataSet ก็ต้องใช้ → เพิ่ม `code` มีเหตุผลในตัวเอง ไม่ใช่การยัดเรื่องคืนยาเข้า master

**คำถามที่รอผู้ใช้ตอบ:** `return_source` มี 5 ค่า (`ward`/`or`/`er`/`opd`/`vendor`) ออกแบบตอน dropdown มีแต่หน่วยงานใน รพ. แต่พอยุบ master แล้ว `รพสต.` · `ศูนย์บริการสาธารณสุข 2/3/4` · `เทศบาลนครรังสิต` · `รพ.ลาดหลุมแก้ว/สามโคก/เปาโล` + กลุ่ม `รพ.อื่นยืมยา/คืนยา` (จาก ADR-0020) **จะตกเป็น `ward` หมด ซึ่งผิดความหมาย** → จะเพิ่มค่าที่ 6 เช่น `external` ไหม

**คำแนะนำที่ให้ไป:** เพิ่มครับ และ derive จาก `location_type` ที่แผนข้อ 1 มีอยู่แล้ว (`ในโรงพยาบาล` → ward/er/opd ตาม code · `ปฐมภูมิ` + `ภายนอก` → `external` · vendor แยก) — mapping ไม่ผูกกับชื่อไทย และไม่ต้องมีคอลัมน์ `return_source` ใน master ให้ context คืนยารั่วเข้ามา

**จังหวะสำคัญ:** `return_logs` มี **0 แถว** → เปลี่ยน taxonomy ตอนนี้ไม่ต้อง migrate เลย ถ้าปล่อยจนมีข้อมูลแล้วค่อยแก้ ต้อง backfill

**ถ้าผู้ใช้ตกลง:** เสนอทำ `docs/adr/0003-return-source-derived-from-department.md` เป็น **Superseded** พร้อม ADR ใหม่ — ADR เดิมระบุเองว่า "ไม่แยก `or` เพราะ dropdown ไม่มีหน่วยงานที่เป็นห้องผ่าตัด" ซึ่งเป็นเงื่อนไขที่กำลังจะเปลี่ยนเพราะ master คุมได้แล้ว

### คำถามที่ยังไม่ได้ถาม (ทำต่อได้เลย)

3. `dept_type` ต้องมีค่าสำหรับ **กลุ่มที่ยุบมาแล้ว** หรือไม่ (ดู §0 ข้อ 2 — `ฝ่ายต่างๆ`/`รพสต.`/`รพ.อื่นยืมยา/คืนยา`)
4. `คลังยา` ควรอยู่ใน dropdown "หน่วยงานที่เบิก/คืน" หรือไม่ (เป็น `main_store` — ต้นทางของการจ่าย ไม่ใช่ผู้เบิก แต่มี 6 users + 1,442 audit rows ผูกอยู่)
5. หน่วยงานที่ปิดใช้งาน (`is_active = false`) ต้องยังโผล่ใน **ตัวกรองประวัติ** ไหม (ถ้าไม่ ประวัติเก่าของหน่วยที่ยุบไปแล้วจะกรองไม่เจอ)

## 7. คำถามที่ตอบไปแล้วใน session นี้ (อย่าถามซ้ำ)

- **"แถม" ควรลงราคา 0 หรือเท่าราคาซื้อ?** → **ราคา 0 + รับจำนวนจริง** (มูลค่าคงคลังต้องเท่าเงินที่จ่ายจริงเพื่อ tie-out กับ AP/บัญชี) แต่ต้องแยก "ราคาทุน = 0" ออกจาก "ราคาอ้างอิงสำหรับตีมูลค่าการเบิกใช้" ไม่งั้นตัดจ่ายจาก lot แถมแล้วมูลค่าการใช้ = 0 · ADR-0007 รองรับอยู่แล้ว (price อยู่ในคีย์ของ `stock_ledger` = cost layer)
  - ข้อมูลจริง: ระบบ **ไม่มีหมวด "แถม" เลย** (ค้นทั้ง note / drug_name / log = 0 ครั้ง) และหมวดที่ควรฟรีก็ปนกัน — การซื้อ 2,526 แถว (ราคา 0 เพียง 2) · การยืม 52 (ราคา 0 = 47) · การบริจาค 38 (ราคา 0 = 26 แต่ยังมีมูลค่ารวม 6,509) · การสนับสนุน 19 (มูลค่ารวม 206,211)
- **จ่ายด่วนต้องมีเอกสารให้กรรมการตรวจรับก่อนไหม?** → **ต้องมี แต่คนละใบตามเคส**
  - เคส "ของถึงแล้วยังไม่ตรวจรับ" = ใบส่งของ/ใบวางบิลต้องลงทะเบียนรับและส่งถึงกรรมการแล้ว (ระเบียบกระทรวงการคลังฯ 2560 หมวด 6 ข้อ 175–189 · กรรมการ ≥ 3 คน เว้นวงเงิน ≤ 100,000 บาทตั้งคนเดียวได้ · ใบตรวจรับ ≥ 2 ฉบับ · แหล่งสรุประบุกรอบ 3 วันทำการ · ของที่ยังไม่ตรวจรับเบิกจ่ายไม่ได้)
  - เคส "ของยังไม่มา" = **ใบยืมตามข้อ 207–208** (ลายลักษณ์อักษร + เหตุผล + วันคืน + ผู้อนุมัติ) ตรงกับ `purchase_type = การยืม` 52 แถวที่มีจริงใน DB
  - **ข้อกำหนดที่เพิ่มเข้า roadmap ข้อ 2 จากเรื่องนี้:** บังคับเลือกฐานเอกสาร 1 ใน 2 ตอนบันทึกจ่ายด่วน · เก็บ "ผู้อนุมัติ" แยกจาก "ผู้บันทึก" · สถานะ "รอปลดเปลื้อง" + นับวันค้าง + เตือนเมื่อเกินกรอบ · ปลดเปลื้องผูก Lot + EXP และผูกกับใบตรวจรับจริง (`inspect_meta`) · ห้ามบิลที่มีจ่ายด่วนค้างเดินไปถึง `ap_stage = posted` โดยไม่ผ่าน `inspected`
- **แก้ที่เคยพูดผิดไป:** คอลัมน์ `tpu_code` / `gpu_code` / `ttmp_code` **มีอยู่แล้ว** ใน `receive_logs` แต่ว่างเปล่า 100% (0 จาก 2,659 แถว) → roadmap ข้อ 9 เบากว่าที่ประเมินไว้ schema พร้อม เหลือแค่เติมข้อมูล

## 8. ข้อควรระวังสำหรับ agent ถัดไป

- **Supabase MCP หลุดกลางทาง** — ตัวเลข DB ทั้งหมดในเอกสารนี้มาจาก query ที่รันไว้ก่อนหน้า ถ้าจะรัน migration หรือ verify ต้องต่อ MCP ใหม่ก่อน
- อ่าน `CLAUDE.md` ก่อนเสมอ โดยเฉพาะ **Critical Rule #7** (department 2 ระบบ) · **#12** (sync label 3 ที่) · **#21** (alias pattern) · **#23** (permission key ตรงกัน 3 ที่)
- **Do Not rule ที่เกี่ยวโดยตรง:** ห้ามตัด `เบิกเพิ่มจากความผิดพลาด` / `คืนยา` ออกจาก **ตาราง** เบิก (ตัดได้เฉพาะ dropdown + กราฟ aggregate)
- `npm run lint` ทั้ง repo **ไม่ใช่ 0** (มี error ค้างเดิม ~53 ตัว) → lint เฉพาะไฟล์ที่แก้ แล้วเทียบ baseline ด้วย `git stash`
- **ไม่ commit / push จนกว่าผู้ใช้จะสั่ง**
- ผู้ใช้สื่อสารภาษาไทย · UI ทุกอย่างต้องเป็นภาษาไทย · ห้าม emoji ใน UI (ใช้ `lucide-react`)
