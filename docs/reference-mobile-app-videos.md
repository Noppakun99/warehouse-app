## 3. สิ่งที่นำมาใช้ — เทียบกับ repo (ตรวจ 11/10/2569)

### 3.1 นำมาใช้ได้เลย
1. **รูปแบบหน้าจอมือถือของคลิป 1** — มีแล้ว: แถบแท็บล่างจอ (Phase 3 `BOTTOM_NAV` ใน AppShell) · bottom sheet รายละเอียดแถว (Critical Rule #5) · wizard ทีละขั้น (RequisitionApp) · ยังไม่มี: **ตัวกรองใน bottom sheet** — หน้าประวัติเบิกบนจอ 375 ช่องค้นหา/หน่วยงาน/ชนิดยา/วันที่กินครึ่งจอบนก่อนเห็นข้อมูลแถวแรก (ภาพ `.playwright-mcp/phase3/r03_dispense_mine.png`) → แนวคิด "แถบสรุปเงื่อนไข + ปุ่มกรองเปิด bottom sheet" ของคลิป 1 ช่วยได้
2. **ทดสอบด้วยผู้ใช้ 2 คนพร้อมกัน** ก่อนเปิด pilot เบิกยาออนไลน์ — การจองยาในใบเบิก (ADR-0005 จองระดับรหัส) คือปัญหาเดียวกับการจองที่นั่ง
3. **กฎ "เห็นเฉพาะของตัวเอง" ห้ามไปใช้กับตัวเลขที่ต้องนับรวมทุกคน** — บั๊กคลิป 1 (RLS ซ่อนการจองของคนอื่น → ที่นั่งดูว่าง) เทียบกับเรา: ผู้เบิกเห็นประวัติเบิกเฉพาะหน่วยงานตัวเอง (`normDept` บัตรยา / `dispense-mine`) ได้ แต่ **ยอดจอง/คงเหลือพร้อมเบิกต้องนับใบเบิกทุกหน่วยงาน** เสมอ
4. **ระวัง AI ทำข้อมูลปลอมที่ดูจริง** — ตรงกับกฎ "อย่าใช้ mock/hardcode data ใน component" ของเรา: ตรวจโค้ดที่ AI เขียนว่าตัวเลขบนจอมาจาก query จริง (เทียบกับ DB แบบ Rule #6) ไม่ใช่ค่าสุ่ม/ค่าคงที่
5. **บั๊กข้อมูล → log request/response ก่อนเดา** — ตรงกับ Critical Rule #9 (เช็ค SQL/DB ก่อนแก้โค้ด)
6. **ให้ภาพอ้างอิงก่อนออกแบบหน้าตา** (คลิป 2) — เราทำแล้วตอนออกแบบ Dashboard (ศึกษา Dribbble — handoff Dashboard §7) ใช้ต่อกับหน้ามือถือหน้าอื่น
7. **สรุปแล้วเปิดแชทใหม่แทน compact** (คลิป 2) — ตรงกับ `/handoff` ที่ใช้อยู่

### 3.2 ห้ามลอก (จุดอ่อนในคลิป)
- **"ล็อกที่นั่ง" ในคลิป 1 ไม่ใช่การล็อกจริง** — แค่อ่านการจองที่ยืนยันแล้วตอนเปิดหน้า · สองคนกดจองที่นั่งเดียวกันพร้อมกันยังได้ทั้งคู่ · "ถือราคา 10 นาที" ที่พูดตอนต้น (1:05) ไม่ได้ทำ → **การจองยาของเราต้องบังคับตอนเขียน (constraint/transaction ฝั่ง DB) ไม่ใช่แค่ตอนแสดงผล** — ผูกกับข้อ 3.8 "ความเสี่ยงคีย์ซ้ำ" ที่ค้างก่อน pilot
- **คลิป 1 วาง service_role key ลง `.env` ของแอปมือถือ** (21:53) — ค่าใน env ฝั่ง client ถูกฝังในแอปที่แจกผู้ใช้ = ใครก็ได้สิทธิ์แอดมินฐานข้อมูล · **ของเราตรวจแล้วถูกต้อง:** `.env` มีแค่ `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` · service_role อยู่ใน edge function เท่านั้น (เช่น `line-tasks`) · `.env` อยู่ใน `.gitignore` แล้ว
- **คลิป 1 แก้ SQL error ด้วยการตัดสิทธิ์แอดมินทิ้งทั้งชุด** (11:44) — แก้ให้ error หายแทนแก้สาเหตุ · เรายอมรับ anon key เต็มสิทธิ์ไว้แล้วโดยรู้ตัว (ADR-0016) — ถ้าขยายผู้ใช้ (PWA/เปิด pilot) ให้ทบทวน ADR นั้น ไม่ใช่ตัดการป้องกันเพิ่ม
- Sanity CMS / Stripe / เขียนใหม่ด้วย Expo — ไม่ตรงงานเรา (ต้นทางข้อมูลคือไฟล์ Excel ของคลัง)

### 3.3 ช่องว่างมือถือของแอปเรา — ผลหลังลงมือ (11/10/2569)
- **PWA ✅ ทำแล้ว:** manifest + ไอคอน (วาดจากโลโก้ Pill) + meta · **ไม่มี service worker** · Chrome ยอมรับว่าติดตั้งได้ (CDP `Page.getInstallabilityErrors` ว่าง — tests/15) · ปุ่มย้อนของมือถือ = กลับหน้าก่อน/ปิดบัตรยา (ผูก navStack กับ history — ไม่งั้นแอปที่ติดตั้งบน Android กดย้อนแล้วปิดแอป) · login ยังเก็บ `sessionStorage` (ปิดแอป = ออกจากระบบ — ตัดสินแล้ว)
- **"3 หน้าไม่มีโหมดมือถือ" ที่เขียนไว้ตอนแรก — ผิด:** นับ `<table>` แบบหยาบ รวมตารางในใบพิมพ์ (HTML string) · สำรวจจริงที่ 375px ทุกหน้าที่ผู้เบิกเข้าได้: **ไม่มีหน้าไหนเลื่อนแนวนอนทั้งหน้า** · ยืม-คืนยาเป็นการ์ดอยู่แล้ว · Stockcard มีโหมดการ์ด `md:hidden` · วิเคราะห์การเบิกมีแค่ตารางคาดการณ์ (แท็บแนวโน้ม) กว้างเกิน 61px เลื่อนในกล่องตัวเอง → ไม่ต้องทำ (ภาพ `.playwright-mcp/mobile-survey/`)
- **ตัวกรอง sticky กินจอ ✅ แก้แล้ว (สำคัญกว่าที่คิด):** การ์ดตัวกรองประวัติเบิก/รับยาเป็น `sticky top-14` ค้างจอตลอดการเลื่อน — ประวัติรับยากิน 204px · ประวัติเบิก ~200px → `FilterSheet.jsx` (มือถือ = ช่องค้นหา + ปุ่ม "ตัวกรอง (N)" + บรรทัด "กรอง: …" + bottom sheet · คอม layout เดิม) → ประวัติเบิกเหลือ 64px
- พบระหว่างสำรวจ (ของเดิม ไม่แก้): แท็บหน้าวิเคราะห์การเบิกใช้ emoji (ผิดกฎห้าม emoji ใน UI) · การ์ดสถิติประวัติเบิกตัวเลขมูลค่าล้นการ์ดที่ 375

## 4. งานที่เสนอ — สถานะ (11/10/2569)
1. ✅ PWA แบบไม่มี service worker + ปุ่มย้อน — **iPhone เครื่องจริงผ่านแล้ว 11/10/2569** (ติดตั้ง/เต็มจอ/ย้อนกลับ/หน้าพิมพ์ Blob URL กลับเข้าแอปได้) · Android ยังไม่ได้ลองเครื่องจริง
2. ❎ ไม่ต้องทำ (ข้อ 3.3)
3. ✅ ตัวกรองมือถือ → bottom sheet (ประวัติเบิก + ประวัติรับยา)
4. ⏸ รอตัดสิน — ไล่โค้ดแล้ว **ช่องโหว่มีจริงแบบเดียวกับคลิป**: `submit` ใน RequisitionApp ตรวจคงเหลือ−ยอดจองฝั่งเบราว์เซอร์ แล้ว insert `requisitions` + `requisition_items` เป็น 2 คำสั่งแยก ไม่มีล็อก/transaction → 2 หน่วยงานกดส่งพร้อมกันผ่านทั้งคู่ (จองเกินของ) · insert รายการล้ม = หัวใบเบิกเปล่าค้าง · ทางแก้ = ฟังก์ชัน DB (RPC) ล็อกต่อรหัสยา + ตรวจ + insert ในธุรกรรมเดียว (repo ยังไม่เคยใช้ `rpc()` — ต้อง ADR + migration) · ทดสอบ 2 ผู้ใช้พร้อมกันต้องเขียนข้อมูลจริง (ไม่มี DB ทดสอบแยก) → ทำหลังได้รับอนุญาตเท่านั้น
