## ตารางรอบ

| วัน | เหตุการณ์ |
|---|---|
| จันทร์ | ส่งใบเบิก (รอบ 1) |
| อังคาร | มารับของ (รอบ 1) |
| พุธ | ส่งใบเบิก (รอบ 2) |
| พฤหัส | มารับของ (รอบ 2) |

**ประกาศ 4 ครั้ง/สัปดาห์** — ประกาศมี 2 ชนิด (`kind`) วันหนึ่งเป็นได้อย่างเดียว:

| kind | วัน | ข้อความ |
|---|---|---|
| `requisition` | จันทร์ / พุธ | "ส่งใบเบิกมาได้เลย" + บอกวันมารับของ |
| `pickup` | อังคาร / พฤหัส | "วันนี้มารับของได้ 9.00-15.00น." |

### ⚠️ วันรับ **ไม่ได้** มาจาก `REQUISITION_WEEKDAYS`

`REQUISITION_WEEKDAYS` ยังเป็น `[1, 3]` (จันทร์/พุธ) = **วันเบิกเท่านั้น**
ห้ามใส่ `[1,2,3,4]` เพื่อให้ยิง 4 วัน — ระบบจะเข้าใจว่าอังคารเป็น "วันเบิก" แล้วคำนวณวันรับเป็นพุธ (ผิด)
วันรับต้อง derive จากรอบเดิมเสมอ (`pickupDate`) จึงเลื่อนตามวันหยุดถูกอัตโนมัติ

**วันเบิกชนะวันรับ** เมื่อชนกัน — เช่น 14 ต.ค. 2569 เป็นทั้งวันรับ (รอบจันทร์ 12 ที่เลื่อนเพราะ 13 หยุด)
และวันเบิกรอบ 2 → ยิงข้อความเดียวแบบ `requisition` เพราะข้อความวันเบิกพูดถึงวันรับอยู่แล้ว

### โควตา LINE — จะเงียบท้ายเดือนเป็นปกติ

โควตา OA นี้ = **300 ข้อความ/เดือน** · push เข้ากลุ่ม **นับรายหัว** · กลุ่มมี **24 คน** → ยิงได้ **12 ครั้ง/เดือน**

| รูปแบบ | ข้อความ/เดือน | ผล |
|---|---|---|
| **4 ประกาศ/สัปดาห์ (ที่ใช้)** | ~418 | ⚠️ เกินโควตา → **เงียบ ~10 วันท้ายเดือนทุกเดือน** |
| 2 ประกาศ/สัปดาห์ (แบบเดิม) | ~209 | ✅ พอทั้งเดือน แต่ไม่มีประกาศวันมารับของ |

**นี่คือการตัดสินใจที่รับทราบผลแล้ว (2026-08-15)** — เลือกครบ 4 วันโดยยอมให้เงียบท้ายเดือน

### คำเตือนโควตาแจ้ง "ในแอป" ไม่ใช่ในกลุ่ม LINE

⚠️ **ห้ามต่อท้ายคำเตือนโควตาลงในข้อความที่ส่งเข้ากลุ่ม** (เคยทำแล้วถอดออก 2026-08-15)
เหตุผล: เรื่องโควตาเป็นงานหลังบ้านของคลัง — ward รู้ไปก็ทำอะไรไม่ได้ และทำให้ข้อความยาวขึ้นเปล่าๆ

ช่องทางจริง = audit action **`line_quota_low`** → เด้งใน**กระดิ่งแจ้งเตือนของแอป** (staff/admin เห็น;
requester ไม่เห็นเพราะ scope กรองด้วย `department` และบอท stamp เป็น `คลังยา`)

| เมื่อไร | ข้อความในกระดิ่ง |
|---|---|
| เหลือส่งได้ ≤ 2 ครั้ง (`QUOTA_WARN_SENDS`) | "โควตาแจ้งเตือน LINE ใกล้หมด (ใช้ 268/300) — ส่งประกาศเข้ากลุ่มได้อีก 1 ครั้ง" |
| ครั้งสุดท้ายของเดือน | "ส่งประกาศครั้งสุดท้ายของเดือนแล้ว — หลังจากนี้กลุ่มจะไม่ได้รับประกาศจนถึงสิ้นเดือน" |
| วันที่ประกาศไม่ออกเพราะโควตาหมด | "โควตาหมดแล้ว — ประกาศรอบเบิก-รับวันนี้ไม่ได้ส่งเข้ากลุ่ม จะกลับมาส่งอัตโนมัติต้นเดือนหน้า" |

**เพิ่ม action นี้ต้อง sync 3 ที่ตาม Critical Rule #12** — ทำครบแล้ว: `NOTIF_LABELS` + `notifMessage()`
([NotificationBell.jsx](../../src/NotificationBell.jsx)), `NOTIFY_ACTIONS` ([db.js](../../src/lib/db.js)),
`ACTION_LABELS` ([AuditLogApp.jsx](../../src/AuditLogApp.jsx))

**สถานะโควตา ณ 15 ส.ค. 2026**: ใช้ไป 194/300 เหลือ 106 = ยิงได้อีก 4 ครั้ง (จ17 อ18 พ19 พฤ20) แล้วหมด
→ สัปดาห์ 24-31 ส.ค. เงียบ · รีเซ็ต 1 ก.ย.

**ทางแก้ถาวร** = อัปเกรดแพ็กเกจ LINE (การส่งแบบไม่ mention ก็ยังนับรายหัวเท่าเดิม ไม่ช่วยประหยัด)

## สถาปัตยกรรม

```
pg_cron (ทุกวัน 09:00 ไทย)
   └→ Edge Function requisition-announce
        ├→ อ่าน public_holiday (service role)
        ├→ announceSchedule.js: วันนี้เป็นวันประกาศไหม + ข้อความว่าอะไร
        ├→ เช็คโควตา LINE (ไม่พอ → ไม่ยิง + บันทึก audit)
        └→ push textV2 + mention all
```

**`supabase/functions/_shared/announceSchedule.js` เป็น plain JS โดยเจตนา** — Deno import ได้ และ node (golden test) ก็ import ได้ (`package.json` เป็น `type: module`) → **logic อยู่ที่เดียว** ไม่ต้อง sync สำเนา TS เหมือน `swapPolicy` ที่ Critical Rule #11 บังคับ sync 4 ที่

## กฎที่ implement แล้ว

1. **วันหยุด → ไม่ประกาศ** และรอบเลื่อนไปวันทำการถัดไป (เลื่อนทั้งวันส่งใบเบิกและวันมารับของ)
2. **วันรับ = วันทำการถัดไปจากวันส่งใบเบิก** — ปฏิทินชุดเดียว วันรับ derive เอา
3. **วันเบิกชนวันรับได้** — วันหนึ่งเป็นทั้งวันรับ (รอบก่อน) และวันเบิก (รอบใหม่) ไม่ถือว่าผิด
4. **หยุดยาว ≥ 4 วันติด (นับ ส-อา ด้วย) → ยุบเหลือรอบเดียว** + เตือน "เบิกเผื่อวันหยุด" ในรอบสุดท้ายก่อนหยุด
5. **เมื่อเลื่อนต้องบอกเหตุผล** — ทั้งกรณีวันเบิกเลื่อน และกรณีวันเบิกไม่เลื่อนแต่วันรับเลื่อน (ไม่อธิบายเสาร์-อาทิตย์ คนรู้อยู่แล้ว)
6. **"พรุ่งนี้" ใช้เฉพาะเมื่อวันรับเป็นวันถัดไปจริง** — เคสประกาศศุกร์/รับจันทร์ ต้องระบุวันตรงๆ

## `@All` ต้องใช้ `textV2` เท่านั้น

```json
{
  "type": "textV2",
  "text": "📋 {everyone} ฝ่ายไหนจะเบิก ...",
  "substitution": { "everyone": { "type": "mention", "mentionee": { "type": "all" } } }
}
```

**ส่ง type `text` แล้วพิมพ์ `@All` ลงไปตรงๆ = ตัวอักษรธรรมดา ไม่มีใครได้ noti** (บอทเดิมเป็นแบบนี้) ข้อจำกัด: ใช้ได้เฉพาะ reply/push และปลายทางต้องเป็น group/multi-person chat — **OpenChat ใช้ไม่ได้** (Messaging API ไม่รองรับ)

`announceSchedule.js` ใส่ `{everyone}` เป็น placeholder ไว้ให้แล้ว และ golden test มี assertion กันไม่ให้ใครเปลี่ยนกลับเป็น `@All`

## ปฏิทินวันหยุด

**แหล่งความจริง = ตารางที่คนกรอก ไม่ใช่สูตรคำนวณ** เพราะ (1) วันหยุดพุทธศาสนาเลื่อนตามจันทรคติ (2) ครม. ประกาศวันหยุดพิเศษเพิ่มกลางปี

หน้า admin: **ควบคุมระบบ → ปฏิทินวันหยุด** (`page: 'holiday'`, admin เท่านั้น)
มีบล็อก **"ตัวอย่างประกาศ 4 สัปดาห์ข้างหน้า"** แสดงข้อความจริงพร้อม badge `เลื่อน`/`ยุบรอบ`/`เตือนก่อนหยุดยาว` — ใช้ตรวจว่ากรอกถูกก่อนของจริงยิง

### กรอกอัตโนมัติจาก Google Calendar

ปฏิทิน `th.th#holiday@group.v.calendar.google.com` แยกประเภทในฟิลด์ `description`:

⚠️ **รายการนี้ไม่ครบ — ขาดวันหยุดพุทธศาสนา** (มาฆบูชา/วิสาขบูชา/อาสาฬหบูชา/เข้าพรรษา) ใช้เป็น**ร่าง**เท่านั้น ต้องมีคนตรวจเทียบประกาศจริงเสมอ

## บันทึกการ setup (2026-08-15)

**`requisition_announce_cron.sql` เวอร์ชันแรกมีกับดัก** — อ้าง vault secret ชื่อ `expiry_alert_auth`
โดยเข้าใจว่า "ใช้ auth ร่วมกับ expiry-alert ได้" แต่ความจริงคือ **vault ว่างเปล่า (0 แถว)** และ
**expiry-alert ไม่เคยตั้ง cron เลย** → ถ้ารันตามไฟล์ cron จะยิงด้วย `Authorization: Bearer ` (ว่าง)
ได้ **401 เงียบทุกวัน** โดยไม่มีใครรู้ (ฟังก์ชันไม่ถูกเรียก จึงไม่มี audit log ให้เห็นด้วย)

แก้แล้วโดยสร้าง secret เอง 2 ตัว: `requisition_announce_auth` (anon key) + `requisition_announce_url`
และ **ต้อง `CREATE EXTENSION pg_net`** ก่อน (ไม่ได้ติดตั้งมาแต่แรก — `pg_cron` มีอยู่แล้ว)

**บทเรียน**: ตั้ง cron เสร็จอย่าเชื่อว่าจบ — ต้อง verify `net._http_response.status_code = 200`
ไม่ใช่แค่ดูว่า `cron.job` มีแถว (ยืนยันแล้ว 200 ก่อนตั้ง cron จริง)
