# Skill: import-excel

นำเข้าข้อมูลจาก Excel เข้าฐานข้อมูลผ่าน CLI — แทนการเปิด Excel → copy sheet → Save As CSV → อัปโหลดผ่านหน้าเว็บ

> **สถานะ:** ครบทั้ง 5 ชีทแล้ว + แตก CSV ได้

## ไฟล์ Excel ที่ครอบคลุม

| ไฟล์ใน OneDrive | ชีทที่ใช้ |
|---|---|
| `ยอดคลังยา_69.xlsm` | Master · เบิก&nbsp;· วิเคราะห์สั่งซื้อ |
| `รับจากการซื้อ_ยืม_ตุลา2567-2569.xlsm` | รับยา · รพ.ยืมยา |
| `รายงานการซื้อยา_69.xlsx` | รายงานซื้อยา · บริษัท_วันที่ล่าสุด_ราคา (แตก CSV อย่างเดียว ยังไม่มีปลายทางในแอพ) |

## คำสั่ง

| คำสั่ง | ชีท | ปลายทาง | วิธีเขียน |
|---|---|---|---|
| `npm run import:receive` | รับยา | `receive_logs` | 🔴 DELETE ALL |
| `npm run import:master` | Master | `inventory` | 🔴 DELETE ALL |
| `npm run import:dispense` | เบิก&nbsp; | `dispense_logs` | 🔴 DELETE ALL |
| `npm run import:reorder` | วิเคราะห์สั่งซื้อ | `drug_reorder_config` | 🟢 UPSERT |
| `npm run import:loan` | รพ.ยืมยา | `drug_loan` | 🟢 diff insert/update |
| `npm run export:csv` | ทุกชีท | `csv_file/*.csv` | เขียนไฟล์ ไม่แตะ DB |

ทุกตัวนำเข้า: dry-run เป็นค่าเริ่มต้น · `--commit` ถึงเขียน · สำรองอัตโนมัติก่อนเขียน

### แตก CSV (แทนการ Save As ทีละชีท)

```bash
npm run export:csv              # แตกทั้ง 7 ไฟล์ลง csv_file/
npm run export:csv -- --list    # ดูรายการก่อน
npm run export:csv -- --only master
```

ได้ไฟล์หน้าตาเดียวกับที่คลังทำมือ (UTF-8 BOM — Excel เปิดภาษาไทยไม่เพี้ยน)
**ไม่ต้องใช้ CSV เพื่อนำเข้าแอพ** — `import:*` อ่าน serial ดิบจาก .xlsm ตรงๆ ซึ่งแม่นกว่า
CSV มีไว้ให้คน/เครื่องมืออื่นอ่าน

## เมื่อไหร่ใช้

- ผู้ใช้บอกว่า "อัพเดตไฟล์เข้าแอพ" / "นำเข้าข้อมูล" / "เอา Excel เข้าระบบ"
- หลังคลังกรอกข้อมูลใหม่ลงชีทแล้วอยากให้แอพเห็น

**เลือกคำสั่งตามสิ่งที่ผู้ใช้กรอก** — ถ้าไม่ชัดว่าแก้ชีทไหน ให้ถามก่อน อย่าเดาแล้วรันทุกตัว

## ก่อนเริ่ม — เช็ค 2 อย่างกับผู้ใช้เสมอ

1. **ปิด Excel หรือกด Ctrl+S แล้วหรือยัง** — CLI อ่านไฟล์จากดิสก์ สิ่งที่พิมพ์แล้วยังไม่ Save จะไม่ถูกนำเข้า
   (ไม่ต้องปิดโปรแกรมก็ได้ แค่ต้อง Save — CLI อ่านอย่างเดียว ไม่ชนกับ Excel)
2. **ถ้าไฟล์อยู่บน OneDrive** — รอ sync เสร็จ (ไอคอนเป็นเครื่องหมายถูก ไม่ใช่ลูกศรหมุน)

CLI จะเตือนเองถ้าเจอไฟล์ `~$...` (Excel เปิดค้างอยู่) และบอกเวลาที่ไฟล์ถูกแก้ล่าสุดทุกครั้ง

## ขั้นตอน

### 1. ดูก่อนว่าจะเกิดอะไร (ไม่เขียนอะไรทั้งนั้น)

```bash
node scripts/import-receive.mjs     # หรือ import-master / import-reorder / import-loan
```

**dry-run เป็นค่าเริ่มต้นโดยเจตนา** — กดลูกศรขึ้นซ้ำคำสั่งเก่าแล้วจะไม่มีอะไรเสียหาย

อ่านผลแล้วเช็ค:
- **เวลาที่ไฟล์ถูกแก้ล่าสุด** ตรงกับที่ผู้ใช้เพิ่งกรอกไหม
- **จำนวนแถว** เทียบของเดิม — เพิ่มขึ้นตามจำนวนบิลใหม่ไหม
- **ช่วงวันที่** ขยายมาถึงวันที่กรอกใหม่ไหม
- **5 แถวล่าสุด** มีบิลที่เพิ่งกรอกไหม
- **ด่านตรวจผ่านหมดไหม**

### 2. เขียนจริง

```bash
node scripts/import-receive.mjs --commit
```

ลำดับที่เกิดขึ้น: อ่านไฟล์ → อ่านของเดิมใน DB → ด่านตรวจ 6 ด่าน → **สำรองข้อมูลอัตโนมัติ** → เขียน → นับแถวเทียบ

**สำรองไม่สำเร็จ = ไม่เขียน** ไม่มีข้อยกเว้น

> ⚠️ **`--commit` ไม่ใช่ `git commit`** — มันคือ "ปุ่มอัปโหลด" ที่เคยกดบนหน้าเว็บ
> อธิบายกับผู้ใช้ด้วยคำนี้เสมอ อย่าพูดลอยๆ ว่า "ต้อง commit ก่อน" เพราะผู้ใช้จะเข้าใจว่าเป็น git
> (เกิดจริง 2026-09-22 — ผู้ใช้ถามว่า "ถ้า copy sheet ไม่เห็นต้อง commit")

**dry-run แล้วไม่ `--commit` = ยังไม่มีอะไรเข้าระบบ** — ถ้าผู้ใช้บอกว่า "กด refresh ในแอพแล้วของใหม่ไม่ขึ้น"
ให้เช็คก่อนเลยว่ารัน `--commit` ไปหรือยัง อย่าเพิ่งไปไล่หาบั๊กในแอพ (เสียเวลาไปแล้ว 1 รอบ 2026-09-22)

**ผู้ใช้สั่ง "import แล้วให้ขึ้นแอพเลย" = รัน `--commit` ได้ทันทีโดยไม่ต้องถามซ้ำ** (ยังต้อง dry-run ก่อนเสมอ
เพื่ออ่านตัวเลข — แค่ไม่ต้องหยุดรอคำยืนยันระหว่างสองขั้น)

### 3. หลังเขียนเสร็จ — ยังไม่จบ

**ตรวจของจริงที่ผู้ใช้ถามถึงด้วย SQL** ไม่ใช่เชื่อบรรทัดสรุปของสคริปต์:

```sql
select lot, qty, exp, location, receive_status from inventory where code='<รหัส>';
```

แล้วบอกผู้ใช้ว่า **ต้องทำอะไรต่อในแอพ** — import อย่างเดียวมักไม่พอ:

| ถ้ามี… | ต้องบอกให้ทำ |
|---|---|
| รอบตรวจนับประจำปีเปิดค้าง | กด **"รีเฟรชยอดระบบ"** ในหน้ารอบนับ — บรรทัดถูก gen ตอนเปิดรอบ ไม่เห็นของใหม่เอง |
| **มีการแก้ `lot`** ในชีท | หลังผู้ใช้กดรีเฟรชแล้ว → รัน `node scripts/check-lot-orphans.mjs` **ทุกครั้ง** |
| ทุกกรณี | กด refresh ในแอพ (หรือปุ่ม "โหลดหน้านี้ใหม่") |

**แก้ lot = งานยังไม่จบที่ import** — ปุ่มรีเฟรชจะ insert บรรทัด lot ใหม่ให้ แต่ **ไม่ลบบรรทัด lot เก่า**
เหลือ 2 บรรทัดนับซ้ำ (ของ 60 → ใบรับรองรายงาน 120) ดู §"แก้ / ลบ แถวที่ผิด" ด้านล่าง

### 4. ถ้าต้องกู้คืน

```bash
node scripts/restore.mjs                                    # ดูรายการไฟล์สำรอง
node scripts/restore.mjs backup/receive_logs_<ts>.json      # ดูก่อน
node scripts/restore.mjs backup/receive_logs_<ts>.json --commit   # กู้จริง
```

เก็บ 10 ไฟล์ล่าสุดต่อตาราง (ไฟล์ละ ~5 MB) `backup/` อยู่ใน .gitignore แล้ว

| `app_only_data` | บิลสแกน AI / รูปตรวจรับ / บิลที่เดิน AP จะหาย | ⛔ |

### `--force` — ใช้เมื่อไหร่

ข้ามด่านที่บล็อกไว้ **ต้องรู้ว่ากำลังทำอะไร** กรณีที่ใช้ได้จริง:
- ตั้งใจลบแถวออกจากชีท (ไฟล์เลยดู "เก่ากว่า" DB) → `stale_file` ยิงทั้งที่ถูกต้อง
- ตั้งใจล้างข้อมูลเก่าทิ้งจริงๆ

**อย่าใช้ `--force` เพื่อให้ผ่านๆ ไป** — ด่านที่ยิงแปลว่ามีอะไรผิดปกติ อ่านเหตุผลก่อนเสมอ
ถ้าจะย้อนข้อมูลกลับ **ใช้ `restore.mjs` ดีกว่า `--force`** เพราะได้ snapshot ที่แน่นอน

## ⚠️ กับดักที่ต้องรู้

### 1. วันที่ — ห้ามอ่านค่าที่ Excel "แสดง"

คอลัมน์วันที่เก็บเป็น serial (ตัวเลข) แต่รูปแบบที่แสดง **ปนกัน 2 แบบในคอลัมน์เดียวกัน**:
- serial 46226 แสดง `7/23/26` (M/D/YY อเมริกา)
- serial 46281 แสดง `16/9/2026` (D/M/YYYY ไทย)

ถ้าอ่านข้อความที่แสดงแล้ว parse เป็น DD/MM → **เพี้ยน 2,671 จาก 2,852 แถว**
`receiveSheet.js` จึงอ่าน **ค่าดิบ (raw)** เท่านั้น — ห้ามเปลี่ยนเป็น `raw:false`

### 2. คอลัมน์ enum ที่ถูกจัดรูปแบบเป็นเปอร์เซ็นต์

`% คืนโดยประมาณ` ปกติเป็นข้อความ (`100%`, `25-100%`, `ตามจำนวนจริง`)
แต่ถ้าเซลล์ถูกจัดรูปแบบเป็นเปอร์เซ็นต์ Excel เก็บเป็นเลข (`100%` = `1`)
→ ใช้ `percentCellToText()` อ่านค่าที่แสดงแทน (เจอจริงตอนทดสอบ 2026-09-21)

**คอลัมน์วันที่ห้ามใช้วิธีนี้** (ดูข้อ 1)

### 3. ปี พ.ศ. ที่พิมพ์ลงช่องวันที่

คนกรอก `23/09/2570` → Excel เก็บเป็น serial 244980 (= ปี ค.ศ. 2570)
`serialToIso` แปลง พ.ศ.→ค.ศ. เฉพาะช่วงปี 2500–2600 เท่านั้น
ปีนอกช่วง (เช่น serial 80110 = ปี 2119) = ข้อมูลเสียจริง คืน `null`

### 4. lot — ห้ามแตะ

lot จริงมีรูปแบบ `26E266` ซึ่ง regex เลขวิทยาศาสตร์มองว่าเป็น 26×10²⁶⁶
เคยทำ lot หายถาวร 6 แถว (2026-07-29) → `normalizeLot` เก็บตามที่พิมพ์มาเสมอ

### 5. แถวซ้ำใน Excel = ของกองเดียวกัน ต้องบวกรวม ห้ามแยก

ชีทมีหลายแถวสำหรับ (รหัส + lot) เดียวกันได้จริง — รับเข้าคนละครั้ง เขียนคนละบรรทัด
ชัดที่สุดคือ **เวชภัณฑ์ที่ lot = `-`** (ถุงซิบ ขวด ตลับ): 76 แถวในชีท = **58 กลุ่มจริง**
เช่น ถุงซิบชา 9X13 มี 2 แถว (85 + 100) = ของกองเดียวยอด **185**

นิยามที่ทุกฝั่งต้องใช้ตรงกัน: **1 รายการ = 1 คู่ (รหัส + lot)** ไม่ใช่ 1 แถว Excel
- อ่านคงเหลือ → **บวกรวมทุกแถวที่ key ตรงกัน** (เคย dedupe ทับแล้วของหาย 600 vs 6,600)
- lot ว่าง/`-` ต้อง normalize เป็น `-` ตัวเดียวก่อนทำ key ไม่งั้น `''` กับ `-` แยกเป็นคนละกลุ่ม
- **ห้าม key ด้วย lot เดี่ยว** — lot `-` ซ้ำข้ามตัวยาเป็นสิบรหัส ต้อง `code|lot` เสมอ

### 6. receive_logs = DELETE ALL → INSERT

`insertReceiveRows` **ลบทั้งตารางก่อน insert** (Critical Rule #8)
ของที่มีแต่ในแอพ (บิลสแกน AI, รูปตรวจรับ, สถานะ AP) **ไม่มีในไฟล์ Excel จะหายหมด**
→ ด่าน `app_only_data` มีไว้จับเรื่องนี้ ถ้ายิงขึ้นมา **อย่าข้ามด้วย --force**

## `/scrutinize` — ก่อนสรุปว่า "นำเข้าเรียบร้อย"

**ด่านตรวจ 6 ด่านจับได้แค่ความผิดปกติระดับไฟล์** (แถวหด มูลค่าเหวี่ยง วันที่นอกช่วง)
มันไม่รู้เลยว่า *ข้อมูลที่เข้าไปแล้วถูกความหมายไหม* — เรียก `/scrutinize` เมื่อเข้าเงื่อนไขข้อใดข้อหนึ่ง:

- ผู้ใช้ทักว่าผลไม่ตรงที่คาด ("ทำไมไม่ขึ้น" / "ทำไมจำนวนหาย")
- import แล้วมีของใหม่ที่ **ระบบอื่นต้องเห็นด้วย** (รอบตรวจนับ / reorder / กระดิ่ง)
- จะแก้โค้ดตามหลัง import

**สิ่งที่ /scrutinize ต้องทำในบริบทนี้:**

1. **ยืนยันขอบเขตที่ตัวเองแก้จริง** — `git diff --stat` ก่อนพูด
   import เขียน **ข้อมูล** ไม่ใช่ **โค้ด**; ถ้า `git diff` ว่าง = ไม่ได้แก้โค้ดเลย อย่ารับว่าแก้
   (เกิดจริง 2026-09-22: ผู้ใช้สั่ง "/scrutinize ที่แก้โค้ดไป" ทั้งที่ยังไม่มีโค้ดถูกแก้สักบรรทัด)
2. **ตรวจ 1 รหัสที่ผู้ใช้ถามถึงด้วย SQL จริง** เทียบ 3 ชั้น: ชีท → `receive_logs` → `inventory`
3. **อ่านโค้ดปลายทางก่อนเดา** ว่าฟีเจอร์ไหนจะเห็น/ไม่เห็นของใหม่ — `grep` ฟังก์ชันจริงแล้วดูว่ามี
   `insert` หรือแค่ `update`, filter ตัดอะไรทิ้ง
   (เกิดจริง 2026-09-22: เดาว่าปุ่ม "เพิ่ม lot ที่ระบบว่าหมด" ใช้แก้ได้ — พอเปิดโค้ดจริงมันกรอง
   `system_qty <= 0` ทิ้ง lot ใหม่ที่มีของ แนะนำผู้ใช้ไปผิดทาง)
4. **นับ key ให้ตรงนิยาม "1 บรรทัด = 1 (รหัส + lot)"** — ไม่ใช่ 1 แถว Excel
   ตรวจด้วย SQL ที่ group แบบเดียวกับโค้ดก่อนเชื่อว่าไม่มีบรรทัดซ้ำ

**ห้ามสรุปว่า "เรียบร้อย" ถ้ายังไม่ได้ query ของจริง** — บรรทัด `✓ เสร็จ` ของสคริปต์บอกแค่ว่า
จำนวนแถวตรงกับไฟล์ ไม่ได้บอกว่าผู้ใช้จะเห็นของในแอพ

## แก้ / ลบ แถวที่ผิด — หลักการ (2026-09-23)

`import` ซ่อมข้อมูลที่ผิดใน **ตารางที่ไฟล์เป็นเจ้าของ** ได้เอง (เขียนทับทั้งตาราง)
แต่ของที่ **แตกหน่อไปอยู่ตารางอื่นแล้ว** import ไม่ตามไปแก้ให้ — ต้องไล่เก็บเอง

**ลำดับที่ต้องคิดทุกครั้งที่แก้ค่าที่เป็น "รหัส" (lot / รหัสยา / เลขบิล):**

1. **แก้ที่ชีทต้นทาง → import** — ตารางที่ไฟล์เป็นเจ้าของจบตรงนี้
2. **ถามว่าใครถือค่าเก่าอยู่อีก** — `code|lot` เป็น key ที่หลายตารางใช้จับคู่กัน
   แก้ที่ `inventory` อย่างเดียวแต่ `receive_logs` ยังถือค่าเก่า = การ์ดคลัง lot มองเป็นของ 2 กอง
   **grep หาตารางที่ key ด้วยค่านั้นก่อนสรุปว่าแก้ครบ**
3. **ตารางที่ append-only (`stock_count_item` — ADR-0008) import ไม่แตะ** ต้องจัดการมือ

**เกณฑ์ลบแถวในตาราง append-only:**

| สภาพแถว | ทำได้ไหม |
|---|---|
| **ยังไม่มีผลนับ** (`counted_qty IS NULL`) = งานที่ระบบ gen รอไว้ | ✅ ลบได้ — ยังไม่ใช่หลักฐานอะไร |
| **มีผลนับแล้ว** = คนเดินไปนับมาจริง | ⛔ **ห้ามลบ และห้ามอัปเดตทับ** — ดูด้านล่าง |

**บรรทัดที่นับไปแล้ว ห้ามแตะทั้งลบและแก้** — ผลนับคือ *สิ่งที่คนเห็นบนชั้นวาง ณ เวลานั้น*
ไม่ใช่ค่าที่ต้องทำให้ตรงกับระบบทีหลัง. แก้ทับ = ลบหลักฐานว่าเคยมีส่วนต่าง (ADR-0008 append-only)

ถ้า lot ในระบบเปลี่ยนหลังคนนับไปแล้ว → **ปล่อยบรรทัดนั้นไว้อย่างนั้น** ของที่นับถูกต้องแล้ว
สิ่งที่ต้องแก้คือ *ต้นทาง* (ชีท) ไม่ใช่ผลนับ. อยากบันทึกว่า lot จริงคืออะไร → กรอกช่อง
**"lot ที่นับได้" (`counted_lot`)** ซึ่งเป็นคอลัมน์แยกสำหรับสิ่งที่คนเห็นจริง — `lot` เป็น snapshot ของระบบ
คนละคอลัมน์ คนละความหมาย **ห้ามเอาค่าใหม่ไปทับ `lot`**

**ลบแล้วต้องครบ 3 อย่างเสมอ** (ไม่มีฟังก์ชันลบใน `db.js` โดยเจตนา — เคสที่รู้จักแล้วใช้
`check-lot-orphans.mjs` ด้านล่าง ซึ่งทำครบ 3 ข้อนี้ให้; เคสอื่นเขียนสคริปต์ชั่วคราวตามแบบเดียวกัน):
1. **สำรองแถวเป็น JSON ก่อน** ลง `backup/` — ลบแล้วย้อนไม่ได้
2. **ด่านกันลบผิดตัว** — เช็ค `counted_qty IS NULL` + `code`/`lot`/`session_id` ตรงกับที่ผู้ใช้ยืนยัน
   ไม่ตรงสักอย่าง = หยุด ไม่ลบ
3. **เขียน audit log** พร้อม `reason` + path ไฟล์สำรอง (Critical Rule #1)

**ถามผู้ใช้ก่อนลบเสมอ** — ลบข้อมูลจริงย้อนไม่ได้ ไม่ใช่ของที่ตัดสินใจแทนได้

### แก้ lot ที่ผิด → รอบนับจะได้แถวซ้ำเสมอ (เกิดจริง 2026-09-23)

lot ยาธาตุผสมอบเชย `CL690` → `CL69018` · แก้ชีท Master → `import:master` → กด **"รีเฟรชยอดระบบ"**

**`refreshAnnualCountSystemQty` ([db.js](../../../src/lib/db.js) `refreshAnnualCountSystemQty`) ทำ 2 อย่าง —
ต้องรู้ทั้งคู่ ไม่งั้นแนะนำผู้ใช้ผิด:**

| | พฤติกรรม |
|---|---|
| แถวที่มีอยู่แล้ว | update แค่ `system_qty` / `system_exp` / `system_location` — **ไม่แตะ `lot`** |
| lot ที่ยังไม่มีในรอบ + `qty > 0` | **insert บรรทัดใหม่ให้อัตโนมัติ** |

ผลคือ lot ใหม่ **ได้บรรทัดถูกต้องเอง** แต่ **บรรทัด lot เก่าไม่ถูกลบ** → เหลือ **2 แถว นับซ้ำ**
(ของ 60 ขวด → ใบรับรองรายงาน 120 + มีบรรทัดผี)

**ตั้งใจให้เป็นแบบนี้** — [db.js](../../../src/lib/db.js) `if (!c) continue` คอมเมนต์ว่า "lot หายจาก inventory — คงยอดเดิมไว้
ให้คนไปเช็คเอง": ถ้าลบอัตโนมัติแล้วแถวนั้นมีผลนับอยู่ = ทำลายหลักฐาน ผิด ADR-0008
**ระบบจึงไม่ลบให้ คนต้องเก็บกวาดเอง** → ใช้เกณฑ์ลบข้างบน

### ตรวจ + ถามก่อนลบ — `check-lot-orphans.mjs`

**หลัง `import:master` ที่มีการแก้ lot ต้องรันทุกครั้ง** (หลังผู้ใช้กดรีเฟรชยอดระบบแล้ว):

```bash
node scripts/check-lot-orphans.mjs            # ดูอย่างเดียว
node scripts/check-lot-orphans.mjs --commit   # ลบ — ถามยืนยันทีละคู่ [y/N]
```

หาคู่บรรทัดที่ **ทุกฟิลด์เหมือนกัน ต่างแค่ `lot`** แล้วแสดงเทียบข้างกัน เก่า/ใหม่ + สถานะนับ
**ไม่ลบเองเด็ดขาด — ถามผู้ใช้ทีละคู่เสมอ** (default = ไม่ลบ กด Enter เปล่าคือข้าม)

**⚠️ เกณฑ์ชี้ขาดคือ "lot เก่าหายจาก `inventory` แล้ว" ไม่ใช่ "ฟิลด์อื่นเหมือนกัน"**

ยาจากบิลเดียวกันมักมี lot ไล่กันและ qty/exp/ที่เก็บ **เท่ากันเป๊ะ** — เป็นของจริงคนละกอง ห้ามลบ:

| เคส | lot เก่าใน inventory | แปลว่า |
|---|---|---|
| `1670042` CL690 → CL69018 | ✗ หายแล้ว | **lot ถูกแก้** → บรรทัดเก่าเป็นของซ้ำ ลบได้ |
| `1000211` 60325 / 60326 | ✓ ยังมีของ | **ของจริง 2 กอง** → ห้ามแตะ |

เวอร์ชันแรกดูแค่ "ฟิลด์เหมือนกัน" → **จับผิด 4 เคสรวด จะลบของจริงทิ้ง** (ทดสอบเจอ 2026-09-23)
ด่าน `isLive(older) || !isLive(newer)` คือตัวกันเรื่องนี้ **ห้ามถอดออก**

**ด่านกันลบหลักฐานอีก 2 ชั้น** (ADR-0008) — เจอแล้วข้ามอัตโนมัติ ไม่ถามด้วยซ้ำ:
- บรรทัดเก่า **มีผลนับแล้ว** (`counted_qty != null`) → บอกให้ไปแก้ช่อง "lot ที่นับได้" ในแอพแทน
- บรรทัดเก่า **มีหมายเหตุ / `counted_lot`** ที่คนพิมพ์ไว้

ลบแล้วได้ครบ: สำรอง JSON → `delete ... .is('counted_qty', null)` (กันแข่งกับคนที่เพิ่งนับ) → audit `delete_annual_count_line`

⚠️ **บทเรียนการอ่านโค้ด (2026-09-23):** ตอนแรกสรุปว่า "ปุ่มรีเฟรชแก้ไม่ได้" เพราะอ่านเจอแต่ท่อน `update`
แล้วหยุด — ไม่ได้อ่านต่อถึง block `added` ที่ insert ให้ **อ่านฟังก์ชันให้จบก่อนสรุปว่ามันทำอะไรไม่ได้**
(audit log เป็นตัวชี้ขาดว่าแถวมาจากไหน — `refresh_annual_count_qty` มี `added_sample` บอกตรงๆ)

## กับดักเฉพาะไฟล์ — เบิก&nbsp;→ dispense_logs

- **ชื่อชีทมีเว้นวรรคต่อท้าย** (`'เบิก '`) เรียกผิดตัวเดียวก็หาไม่เจอ
- **หัวตารางอยู่แถวที่ 6** — แถว 1–3 เป็นบล็อกจดลอย (ชื่อยา + ตาราง Lot/Exp เล็กๆ)
  `findHeaderRow` ต้องเจอทั้ง "วันที่เบิก" **และ** "ปริมาณ (ออก)" ไม่งั้นจับบล็อกจดผิดแถว
- **`Math.floor` ไม่ใช่ `Math.round`** — serial ที่มีเศษคือ *เวลา* ของวันนั้น
  (`46202.58` = 29 มิ.ย. 13:54) ถ้า round เศษ ≥ 0.5 จะกลายเป็นวันถัดไป
  **บั๊กจริง: 1,316 จาก 8,058 แถวเลื่อน +1 วัน** (เจอ 2026-09-21 ตอนเทียบกับ DB)

  ไม่งั้น import ทุกรอบจะเห็นว่า exp "เปลี่ยน" ทั้งตาราง

- **ไม่ลบแถวที่หายจากไฟล์** เว้นแต่สั่ง `--delete-missing` (อาจเป็นของที่ยังค้างคืนจริง)
